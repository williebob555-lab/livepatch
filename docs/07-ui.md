# 07 — UI, Rendering, and Interaction

_Last verified: 2026-08-14. Files: `src/ui/*`, `src/ui/visuals/*`, `src/main.ts`,
`src/dockwindow.ts`, `index.html`, `dock.html`, `src/styles.css`._

The workspace is a single immediate-mode `<canvas>`; tool panels are DOM managed
by a dock. There is no per-block DOM — everything on the canvas is drawn each
frame.

## Cable bundling

Wires sharing a `Wire.bundle` id are laid into a ribbon. The rules live in
[`src/ui/bundling.ts`](../src/ui/bundling.ts) as pure geometry —
`Renderer.applyBundles` only collects the groups and puts the results back in the
path cache — so they can be measured without a canvas. **Run
`node scripts/bundle-route-test.mjs` after touching any of this**; it checks
every claim below across three wire styles and five geometries.

### Members are SPLICED, not blended

A bundled member is three pieces joined end to end:

1. its own routed lead-in, from its port to where it meets the corridor,
2. **the offset corridor** — a sub-path of the longest member, shared by all,
3. its own routed lead-out, back to its far port.

The middle is then correct by construction: the right style, and exactly
parallel to its neighbours for as long as the corridor lasts. Both joins are
produced by `routePoints` — the same router every other cable uses — so the
style survives at the ports, which is where the eye checks it.

Two earlier designs failed, and the reasons are worth keeping:

- **v1 replaced the member with `[start, ...offsetLeaderMiddle, end]`**, so the
  joins were straight chords whatever `theme.wireStyle` said. That is the
  "goes straight instead of following the appearance option" report.
- **v2 *blended* each member toward its lane** over a smooth window. It fixed
  the ports and broke the middle: *a weighted average of two axis-aligned
  polylines is not axis-aligned*, so `ortho` bundles came out as diagonals, and
  blending cannot produce a long parallel run either — the members converge to a
  point and separate, which is the "contact is too short" report.

### What each rule is for

| symptom | cause | fix |
|---|---|---|
| bundled `ortho` comes out as diagonals | members blended toward the lane; also `offsetPolyline` moved each vertex along the *average* of its two normals, which is one `d` short at a right angle | splice; and `offsetPolyline` now uses a true miter (`d / cos(half-angle)`, clamped), so a parallel copy of an axis-aligned path stays axis-aligned |
| cables overlap inside a ribbon | lanes packed by `theme.wireWidth` alone — but `drawWire` adds `wireBorderWidth` **each side**, and `wireWideExtra` for a multichannel bus. A 6.5-unit cable in a 7.5-unit lane pitch: less daylight than the border it is drawn with. | `Renderer.bundleHalf` packs by the width the cable is actually drawn at. `bundleSpacing` is now the **gap** on top of that, default `0` — cables touching and not overlapping, which is what a bundle should look like |
| cables cross, worst where several arrive at one block | lane order came from sorting wire **ids** | ordered by which side of the corridor each cable approaches from, averaged over its two ends |
| a two-wire bundle is one straight cable and one displaced one | the leader kept its centre line while everyone else moved | every member takes a lane; the ribbon straddles the route |
| a lead-in ran 1.0 unit from a neighbour's lane, parallel, for 25 units | `ortho` changes axis halfway by default — which is exactly where the other lanes are | joins are routed with `turn: 'late'`, changing axis at the corridor, so a cable runs out along its own port's line and crosses the other lanes square |
| kinks where a cable meets the ribbon | the set-back that gives a join room was a constant, so a breakout came out as a stub, a long sideways move and another stub — two corners crammed together beside the port | the set-back **is** the sideways travel, so a breakout is a square dog-leg (as long as it is wide) and collapses to nothing when the port is already on its lane |
| a `curved` bundle came out as a row of **hairpins** | the joins were handed the corridor tangent pointing *into* the corridor. `routePoints` builds `c2 = b.pos + b.dir × pull`, so the curve **arrives at `b` travelling in `−b.dir`** — every join therefore arrived at the ribbon backwards, overshot and doubled back | `tangentOut` — `EndInfo.dir` points *away* from its end, like a port normal. `ortho` never showed it because it only reads `a.dir` |
| the cable that owns the corridor wiggled at both ports | the lane stack was **centred** on the corridor, which pushes even the member whose own route the corridor *is* half a lane off its own line — a 3.3-unit step and back, beside each of its ports | the stack is **anchored** to whichever member needs to move least, so that one keeps its line exactly and gets no breakout at all |
| a knot of little loops where curved cables meet the ribbon | `routePoints` floors the bezier pull at 30 units so short cables bulge; a join can be 5 units long | `turn: 'late'` also keeps the pull inside the span |

Four things that are easy to get wrong here, and were, in this order:

1. **Endpoints are sacrosanct.** A bundled cable still starts and ends exactly on
   its ports. Verified by measurement, not by eye: port shift is `0.0000` at both
   ends of every member, in every scenario the test runs.
2. **Match ends by NEAREST point on the corridor, not by arc ratio.** Two cables
   of different lengths sharing a run have different parameterisations, and
   matching by ratio slides them along each other. Nearest-point also makes each
   lead-in a perpendicular foot, so it can never double back along the corridor.
3. **Bundling is a request for cables to run together, so members DO move.** An
   attempt to stop the yanking by refusing to gather distant cables made
   deliberate bundles do nothing at all (measured: max displacement fell from 111
   units to 3.8, and no ribbon formed).
4. **A breakout is as long as it is wide.** The set-back where a member joins
   the corridor equals how far that end has to travel sideways to reach its
   lane. A *fixed* set-back lays a fixed length of cable parallel to the ribbon
   whatever the sideways distance is, so a port that happens to sit near a lane
   gets a long run alongside its neighbour (measured 23 units at 3.75 apart); a
   *shorter* one turns the breakout into a stub, a long sideways move and
   another stub, which reads as a kink. Capped at `BREAKOUT_SHARE` of the
   corridor per end, or a cable with a long way to travel spends the whole
   bundle leaving it (measured: shared run 106 → 41).

**Leaving a bundle is the same gesture as joining one.** Dropping a wire end
within `BUNDLE_SNAP` (14 world units) of another cable bundles them; dropping it
away from every bundle-mate takes it out. It used to be a right-click menu item,
which is neither discoverable nor available while you are already holding the
wire. A bundle reduced to one member clears itself, so no invisible group
lingers.

**A cable also leaves the ribbon mid-drag**, once the end you are holding is
`BUNDLE_BREAK` (48 world units) clear of every mate — `Editor.breakBundleIfPulledAway`.
Waiting for the drop is what made pulling a cable out feel stuck: the end follows
your pointer while the rest of the cable stays dressed into its lane, so you
cannot tell whether letting go will free it. The two thresholds are the same
boundary crossed in opposite directions and are deliberately far apart; equal
ones would make a cable held near the edge of the ribbon leave and rejoin every
frame.

**Grabbing a cable end is decided by ENDS, not by bodies.** `paths.hit` returns
the nearest wire *by body distance*, and the endpoint tests then ran against
whatever that returned — so in a bundle a neighbour's body was routinely nearer
than the end you were reaching for, and the press fell through to branch-spawn.
`nearestWireEnd` searches every wire's endpoints first and wins. Separately,
`BASE_END_GRAB` was a flat number of **world** units while the body tolerance was
`WIRE_HIT_TOL / scale + wireWidth`: the two crossed over below about 1× zoom, so
zoomed out the "middle of the wire" band swallowed the "end" band and a press at
a cable end spawned a branch. It is divided by the zoom now, like every other
grab radius.

### What a bundle is measured against

`node scripts/bundle-route-test.mjs` runs five geometries — cables in parallel,
converging on one block, running in opposite directions, entering *adjacent*
ports, and leaving ports that face a different way from their destination —
against each of the three wire styles, and checks:

| contract | what it caught |
|---|---|
| ports unmoved (`0.0e+0`) | v1 moved them |
| every `ortho` segment axis-aligned | the miter bug, worst 0.000u now |
| meets each port no worse than its own route did | joins routed from the corridor let the corridor pick the axis and the far port take what it was given |
| members run together (a share of their length **and** an absolute run) | blending's converge-to-a-point |
| parallel cables never **overlap**, over runs longer than 20 units | the lane-packing and set-back rules above. Touching is the target, so a correct ribbon lands exactly on this floor rather than above it |
| no cable doubles back **alongside itself** | the hairpins. Added after every other contract passed while `curved` bundles were visibly ruined — a hairpin keeps the ports, the spacing and the shared run intact and only wrecks the shape. Total turning cannot express it either: an honest `ortho` member turns six right angles (540°) getting out of a ribbon at both ends. Verified by re-introducing the sign error: self-approach falls from 37u to **3.0u** and the check fails |

Two of those are worth stating as principles, because a stricter-sounding
version of each is untestable:

- **Crossings are not overlaps.** Cables arriving at neighbouring ports have to
  converge; only cables *running together* and touching are a defect.
- **The port-meeting contract is relative to the cable's own route**, not
  absolute. `routePoints` honours the direction of its *first* end only, so an
  unbundled cable can already arrive square across a sideways-facing port.
  Bundling's job is not to make that worse. (It usually makes it better: both
  joins are routed from the port outwards, so both ends get their facing.)

## Render loop (`src/main.ts`)

```
requestAnimationFrame → if (renderer.dirty || runtime.audioOn) {
  runtime.poll(); renderer.draw(editor.overlay); renderer.dirty = false;
}
```

Render-on-demand: idle CPU near zero, but every frame while audio runs (live
meters/visuals). A background `setInterval` re-draws when the tab is hidden (rAF
pauses). A draw error is caught and logged once, never breaking the rAF chain.

## Renderer (`src/ui/render.ts`)

`draw(overlay)` paints, in order: grid → wire paths (level-colored, bordered,
bundled) → wire ends (arrows/terminators) → blocks → overlays (hover ring,
marquee, snap ring). Pan/zoom via `view {x, y, scale}` and `toScreen`/`toCanvas`
(DPR-aware transform).

- **Wire color** = signal level ramp (quiet→good→hot→clip by dBFS thresholds)
  for audio, thickened by level; flat hues for `cv` (purple), `midi` (green),
  `tape` (amber). Levels come from `runtime.levelFor(wireId)`.
- **`drawBlock`** traces the block shape (`traceBlockShape` in `geometry.ts`,
  supporting rect/rounded/chamfer/pill/hex/circle/custom), fills, strokes, then
  draws **face items**, badges (subgraph ⧉, NATIVE), ports, and edit-mode
  handles.
- **Blocks paint in two passes, around the wires.** `BlockStyle.wireLayer:
  'behind'` moves a block into the pass *before* the wires, so cables run across
  its face instead of vanishing under it — which is the only way to read a dense
  patch whose big panels swallow every wire that crosses them.
  `BlockStyle.wireWidth` overrides `theme.wireWidth` for wires touching that
  block (level thickening and the multichannel extra still apply on top). The
  map of overrides is built in `draw` **only when some block declares one**, so
  the common case allocates nothing in a per-frame function; the widest override
  on a wire wins, so a deliberately heavy cable stays heavy along its length
  rather than changing gauge halfway.
- **Hit order follows paint order** (`Editor.wireBeatsBlock`, 2026-08-01).
  `wireLayer` shipped as "paint order and nothing else — hit-testing never sees
  it", and that was wrong: it made the cable the one part of the picture that
  could not be clicked. That reads far worse than not seeing the wire at all,
  because the wire is *right there* and the app appears to be ignoring you. Over
  a `'behind'` block a wire now takes the press, the hover (branch dot and
  `copy` cursor) and the context menu — all three, or the cursor promises a
  branch the press then refuses to make.
  - **Ports are still tested first.** They are ~5 px targets, and pulling a new
    wire out of a panel that already has cables crossing it has to keep working.
  - The block's *widgets* lose to the wire along with its body. A knob a cable
    is drawn over is a knob the cable is in front of, and one rule you can see
    beats two you have to remember; the band is only a few px wide, so the knob
    is still there either side of the cable.
  - `Editor.wireTol` treats `theme.wireWidth` as a **floor** and takes the
    widest `style.wireWidth` in the graph, because a grab band narrower than the
    cable on screen is the same complaint in a different costume. The extra slop
    is free: a press that loses the marquee to a wire still falls back to
    `startMarquee` (see "No drag on the canvas may do nothing").
- **Multichannel wires** read as a *cable*, not a strand. A net wider than
  stereo gets `wireWideExtra` px of thickness plus a lighter inner core
  (`wireCoreColor`), a **channel-count chip** at the trunk's midpoint, and
  **ring ports** at both ends. Hovering it opens a legend naming each channel
  from the Rig's speaker order.
  - N parallel strands were rejected deliberately: that is already what the
    **bundle ribbon** means, and at 12 channels strands are unreadable.
  - The chip shows `2→12` when a narrower port sits on the net. That
    truncation is legal (docs/02) but must never be *invisible* — otherwise
    "why is my surround patch only using two channels" has no visible cause.
  - The chip is suppressed below `view.scale` 0.45 (unreadable) and on branch
    wires (it would restamp the same number beside the trunk's).
  - Width comes from the same rule the compiler uses (widest port on the net),
    recomputed in `draw` — the renderer never reads `CompiledGraph`.
- **Face items** come from `faceItems(b)` (`layout.ts`): `title`, `param:<id>`,
  `visual`, `expose:<childId>`, `link:<childId>:<paramId>`. Each param widget is
  drawn by `paintWidget` (or a special painter for `keys`/`wavedraw`/
  `sampleview`), passed the live value plus the purple post-CV `mod` marker from
  `modOf` → `runtime.modValueFor`.
- **A CV indicator means a cable is patched in — never just that a port exists.**
  Both the live marker and the corner badge go through `cvPatched`
  (`facepaint.ts`), which is `hasCvPort` *plus* `doc.isPortWired`. A
  `cv:<param>` port exists from the moment the user adds it, so keying the
  indicator on the port lit a purple dot on a param nothing was modulating —
  noise, on exactly the widgets whose job is to report what *is* moving. The
  port is already visible on the block edge; the dot has to mean more than that.
  - `hasCvPort` (existence) is kept separate and still drives the **Add/Remove
    CV input** toggles — an added-but-unpatched port must stay removable.
  - Built-in CV inputs use `builtinCvPatched`, same rule. Belt and braces with
    the engine, which also reports `NaN` for an unwired input: the document
    answer works with audio off, the engine answer keeps unwired ports off the
    mods stream.

    **The port id is not the param id (2026-08-02).** `builtinCvPatched` used to
    test `p.id === paramId`. That is true for the three blocks the feature
    shipped with — `panner3d` x/y/z, `amb-encode` x/y/z, `amb-rotate` yaw — and
    false for every one added since: Room's `x` drives `srcx`, Distance's `dist`
    drives `distance`, Ladder's `cut` drives `cutoff`, the VCO's `pitch` drives
    `freq`, Wave Folder's `fold` drives `amount`. Each shipped a CV input that
    moved the audio and left the face perfectly still, and because the check
    *looked* general the bug arrived one block at a time rather than as one
    report about a broken rule.

    The relationship is now declared on the port — `PortSpec.cvParam` plus a
    `cvLaw` — and read back through `cvInputsByParam`, memoized per block **type**
    (this runs once per widget per frame, so it cannot be a scan over
    `def.inputs`; same reasoning as `hasTies`). `scripts/cv-indicator-test.mjs`
    fails the build on a cv input that declares nothing, so the next block
    physically cannot repeat this. See [`08-extending.md`](08-extending.md).
  - **Trigger inputs indicate on the PORT, not on a widget.** A clock, gate,
    trig, sync or reset drives no knob, so there is nothing to mark; the port
    itself wears a halo whose opacity follows the level of the line feeding it
    (`doc.wireIdAtPort` → `runtime.levelFor`, in `drawBlock`'s port loop). A
    clock pulses, a held gate stays lit, an idle line stays dark. It reads
    **peak, not RMS** — a trigger is a spike and RMS over a window averages it
    to nothing — and peak already decays on both engines, which is what makes it
    fade rather than switch. Driven from the wire level both engines publish
    anyway, so it needed no per-kernel edge counter and cannot disagree with the
    cable's own colour.
  - **The web engine reconstructs the value; the native one measures it.** A
    worklet cannot report out of `process()` without allocating
    (`postMessage`), which golden rule 1 forbids, and `SharedArrayBuffer` would
    drag in cross-origin isolation the LAN dock server cannot promise. So
    `webaudio.ts` reuses the analyser tail sample it already reads for wire
    levels and applies the port's declared `cvLaw` (`src/core/cvlaw.ts`) — no
    new node, no new per-frame read. **This is why the law lives on the port:**
    it is the only thing telling the main thread what the DSP did. A law that
    disagrees with its kernel draws a marker that moves the wrong way, which is
    worse than none.
  - **MIDI is deliberately exempt** — a learned binding has no cable to check
    and is live the moment it exists.
  - `doc.isPortWired` walks the **whole scene**, not the open graph, and is
    memoized on `netRevision` like the net index. Both matter: the Dock mirrors
    widgets out of subgraphs, where a graph-local `wireAtPort` would answer "not
    wired" for a perfectly good cable; and this runs once per widget per frame,
    so it cannot be a graph walk (the `resolveAssetFor` cautionary tale in
    [`10-performance.md`](10-performance.md)).
- **`customFace: 'cassette'`** bypasses face items and draws a cassette shell
  (reels, label, duration badge, ⚠ missing-tape state) via `drawCassetteFace`.
- **Live visuals** (`drawVisual`, keyed by `VisualKind`): `eq` is interactive
  and drawn purely from params (no engine needed); `spectrogram` (scrolling,
  per-node offscreen canvas cache), `spectrum`, `scope` (zero-crossing trigger
  lock), `meter` (RMS + peak-hold) are fed by `runtime.visualFor(nodeId)`.
  The `meter` has three looks, chosen by its **`meterStyle` param** — `bar`
  (the classic RMS column + peak hold), `ladder` (a dimming LED segment stack,
  dB-scaled, horizontal when the box is wide) and `lamp` (one dimming LED, no
  frame). It is a *param* and not a `ControlStyle.variant` because a visual is
  not a widget: variants are keyed on `block.controls[ref]` and only ever reach
  `paintWidget`, whereas a visual is painted by `drawVisualAt`, which is handed
  params and nothing else. As a param it also persists, undoes and can be set
  from factory content with no new plumbing. **The LED styles dim by mixing
  toward the unlit colour, never with `globalAlpha`** — `drawBlock` sets
  `globalAlpha` to the face item's own opacity before calling in and only resets
  it after the whole item loop, so writing it would silently discard the user's
  per-item fade for everything painted afterwards. Mixing is also the truthful
  picture: an LED at 20 % is a dim LED on a dark panel, not a translucent one.
  With no feed they draw *dark* rather than printing "audio off" in a box the
  size of a lamp.
  `spatial` (the Spatial Scope) draws the scene's rig from `doc.scene.rig` —
  each speaker at its real azimuth/distance, lit by its channel's live level
  (`feed.chans()`), height speakers ringed. It draws the layout **with audio
  off** and lights up when levels arrive.
  `speakers` (Speaker Rig, Speaker Monitor) draws the same `feed.chans()` data
  as **labelled bar meters** — one column per channel, speaker names from the
  rig, a dB scale with −6/−20 guides, and a clip tell-tale per bar. The two are
  deliberately both available: the radar says *where* the energy is, the bars
  say *how much*, and reading a level off a dot's radius is guesswork.
  On a Speaker Monitor the columns are **clickable** — click to mute, shift-click
  to solo — and silenced speakers draw dimmed with a strike. The column geometry
  lives in `speakerBarSlots`/`speakerBarAt` (`src/ui/widgets.ts`) so the renderer
  and the editor cannot disagree about where a bar is; hit testing is by the
  **whole column**, not the drawn bar, because a bar can be 2 px wide on a
  16-speaker rig and a muted (empty) bar must still be clickable to un-mute.
  When the engine reports a fold (`__folded`/`__chans` on the mods stream, see
  [`05-native-engine.md`](05-native-engine.md)) the visual carries a banner —
  `8 spk → 2 ch · 6 folded`.

## Editor (`src/ui/editor.ts`)

Covered in [`03-document-model.md`](03-document-model.md). It is the sole
interaction controller: a `DragState` state machine handling pan/zoom, marquee
select, block drag/resize, widget operation, wire drag from ports (with
free-floating ends), branch spawn/drop-to-remove, wire bundling, subgraph enter,
and block-edit mode (rearrange/resize face items, slide ports along edges).

Clipboard and grouping shortcuts live here too — **Ctrl+C/X/V** (copy/cut/paste
at the pointer), **Ctrl+D** (duplicate, one grid step away, clipboard
untouched), **Ctrl+G** (group the selection into a block). All four act on the
*whole selection*, which is why the block menu spells the count out. See
[`03-document-model.md`](03-document-model.md) for what travels and what gets
dropped at the boundary.

## Input & navigation — mouse, trackpad, touch, keyboard (`src/ui/editor.ts`)

The app is fully drivable without a mouse. Everything routes through pointer
events plus one keyboard handler, so pen/touch/mouse share the same paths.

- **Canvas needs `touch-action: none`** (`styles.css`, `#canvas`). Without it the
  browser claims touch drags as scroll/pinch and no pointer stream reaches the
  editor. `overscroll-behavior: none` stops a stray swipe navigating away.
- **Pan** — middle-drag or **Space+drag** (mouse), **two-finger drag**
  (touch/trackpad), **trackpad two-finger scroll**, or **WASD** (always) and the
  **arrow keys** (when nothing is selected). Held nav keys drive a small rAF
  velocity loop (`panStep`), speed `14 / view.scale` so it feels constant on
  screen at any zoom. Arrows still **nudge** a selection when one exists — that
  older fine-placement shortcut wins over view-pan, WASD never collides with it.
- **Zoom** — mouse wheel, **pinch** (touch, or trackpad pinch which arrives as
  `wheel` with `ctrlKey`), or `Ctrl/⌘+wheel`. Trackpad scroll vs. mouse wheel is
  disambiguated by `isTrackpadPan` (horizontal component, or fine/fractional
  pixel deltas), made **sticky for 400 ms** so a mid-gesture round-number frame
  doesn't flip pan↔zoom. Plain mouse wheel still zooms — no regression.
- **Classic input escape hatch** (`theme.wheelZoom`, Appearance → Canvas "Mouse
  wheel zooms (classic)"): forces the wheel to always zoom at the cursor and
  disables the trackpad-pan heuristic. Off by default (preserves trackpad
  two-finger-scroll panning). **Turn it on for a hi-res/free-spin mouse wheel**
  whose fine deltas `isTrackpadPan` otherwise misreads as panning — that
  misclassification is the one real mouse-ergonomics footgun of the smart
  default.
- **Two-finger pinch/pan** is a real multi-touch handler: `pointers` (a
  `Map<pointerId, clientXY>`) plus a `gesture` state. The second finger down
  **aborts** any single-finger drag in progress (`abortDrag`, which rolls back a
  moved block, releases held notes, un-pushes a momentary button, deletes a
  just-created wire) and switches to the gesture. `applyGesture` anchors the
  world point under the previous finger-midpoint to the new one, so pan and zoom
  compose with **zero drift** (same math as the wheel-zoom, verified).
- **Context menu without a right button** — **long-press only** (500 ms, one
  finger), and only off the widgets whose press *is* the interaction
  (`ownsHeldPress` / `HOLD_WIDGETS`): buttons, keyboard keys and anything that
  commits where you touched are meant to be held, so a menu there would hijack
  the hold. A knob or fader **does** open it — those change nothing until the
  finger moves — and so does a block's title band, which is the touch route to
  every block-level item. The OS-synthesized `contextmenu` that may follow a
  press is swallowed for 800 ms (`suppressNativeCtxUntil`) to avoid a double.
  - **The two-finger tap was removed on 2026-08-14.** It was the escape hatch
    for widgets long-press is suppressed on, and in practice it mostly fired on
    an *abandoned* navigation: a pinch under `ZOOM_DEADZONE` and a pan under
    `TAP_SLOP` both measure as a tap, so putting two fingers down to move the
    view and changing your mind dropped a menu on the canvas.
  - **Arrange mode replaced it.** In `Mode: Edit` a press moves face items and
    no widget is operated at all (`pointerDown` returns at `editModeDown`), so
    `ownsHeldPress` is false for everything and a hold over a keyboard, a
    momentary button or an XY pad opens that widget's own menu. The mode that
    already turns the interaction off is the touch route to it — no gesture
    invented. See rule 12 of [`14-input.md`](14-input.md).
- Held keys are dropped on window `blur` so pan/`Space`-grab can't stick on.
- UI-scale safe: gesture/wheel/long-press all measure via the canvas
  `getBoundingClientRect` and go through `toCanvas`, the proven scale-cancelling
  path — the main canvas is 1:1, never UI-zoomed (see UI-scale section below).

### Touch rules learned the hard way (2026-07-27)

Four separate reports — "you can't pull blocks out of the library", "moving
blocks for too long prompts the right click", "you can barely control the midi
clip editor" — all reduce to these.

1. **`setPointerCapture` must be wrapped in `try/catch`, always.** It *throws*
   for a pointer id the element never saw; some pen/touch stacks re-issue ids.
   `Editor.pointerDown` called it unguarded as its second statement, so the
   exception aborted the handler **before any hit test ran** and the press did
   nothing at all. Every other canvas in the app already guarded it — the
   workspace was the outlier, and it is the one that matters most.
2. **HTML5 drag-and-drop is mouse-only.** Chromium never synthesizes
   `dragstart` from touch, so the Library's `draggable` tiles were a dead end on
   a touchscreen — double-tap-to-centre was the entire vocabulary.
   `beginTouchDrag` (`src/ui/panels.ts`) is the pointer-event fallback: press,
   drag past a threshold, and a ghost chip follows the finger onto the canvas.
   The threshold is **horizontal**, because the Library scrolls vertically and
   long-press already opens the tile menu — neither of the two obvious gestures
   was free, and a sideways start is neither. A predominantly vertical start
   hands the gesture back to the scroller and never captures the pointer.
   Both drop paths go through `dropLibraryKey`, so mouse and touch land a block
   identically.
3. **Never open a context menu on top of a live drag.** Our own long-press timer
   cancels once a finger travels 10 px, but it is not the only source: Windows
   touch press-and-hold *and* precision-touchpad tap-and-hold both synthesize
   `contextmenu` with their own much looser slop, and a careful, slow block drag
   stays inside it. The result was a block snapping back to where it started
   (`abortDrag`) with a menu over it. The guard is therefore on the **drag**
   (`dragIsLive`, which also covers a 250 ms tail because the synthesized event
   can arrive after the pointerup), not on the source. The same guard is in
   `clipview.ts` and `widgetdock.ts`. Additionally the long-press callback bails
   when `drag.kind === 'blocks' && drag.moved` — `moved` is set by the *first*
   pointermove at any distance, so a precise reposition was being punished for
   being precise.
4. **Grab tolerances must scale with the pointer.** A cursor is a pixel; a
   fingertip is ~10 mm *and hides what it is aiming at*. Ports, wire ends,
   branch roots, roll notes, note stretch handles, play bars and rig speakers
   were all sized for a mouse. Each hit test now takes the pointer type and
   widens by ~2.6× for touch/pen (`grab` in `Editor.pointerDown`, `slop()` in
   `pianoroll.ts`, the `touch` flag on `rigview`'s `hit`). Mouse behaviour is
   byte-identical. The piano roll additionally allows ±1 note row under a
   finger, because a row can be as short as `MIN_ROW` (5 px) and no amount of
   horizontal slop makes a 5 px target hittable — exact-row hits still win.
5. **A 2D editor needs a 2D pinch.** The Clip tab's roll pinch only zoomed
   *time*; `rows` was untouched, so there was no way to zoom pitch by touch at
   all and rows sat near the 5 px floor. `applyGesture` now derives `zoomX` and
   `zoomY` from the fingers' **per-axis** separations, each floored at
   `PINCH_FLOOR` (40 px) — two fingers side by side have a near-zero vertical
   separation, and a ratio of two near-zero numbers would make the pitch axis
   explode the instant they levelled out.

### No drag on the canvas may do nothing (2026-07-25)

**Every press that starts a drag has to end in a `DragState` that does
something.** A branch that sets `drag = { kind: 'none' }` mid-gesture silently
swallows the whole press, and the user reads that as the feature being broken —
not as a near-miss on some other target.

The case that proved it: a wire's hit band is `WIRE_HIT_TOL / view.scale +
wireWidth` wide, so a press within ~7 world px of any wire becomes
`maybeBranch` rather than a marquee. On drag, `maybeBranch` used to check
whether a branch was legal — `arc > BRANCH_DEADZONE` at *both* ends — and where
it wasn't, drop to `kind: 'none'`. So a drag did nothing at all, no marquee, no
branch, not even the wire selected:

- within `BRANCH_DEADZONE` (28 world px of arc) of **either end of any wire**,
  minus the `END_GRAB` ring that legitimately detaches an endpoint, and
- along the **entire length of any wire shorter than `2 × BRANCH_DEADZONE`**,
  which in a dense patch is most of the short hops between adjacent blocks.

It now falls back to `startMarquee(d.start, …)` — the gesture the press would
have got had the hit band not claimed it. A plain *click* still selects the
wire (that path is in `pointerUp`, untouched), and a legal branch drag still
branches. Verified by sweeping ~6800 synthetic drags across visually-empty
canvas at two zooms: **zero** now resolve to `none`.

The wire band is deliberately left wide — narrowing it would make wires hard to
click, trading one complaint for another. The fix is that losing the marquee to
it must still leave you with a marquee.

**Three states also legitimately disable the marquee**, which is worth knowing
before hunting for a bug when a user reports it dead: `overlay.mode === 'edit'`
(the toolbar reads *Mode: Edit*; `E` or `Escape` leaves), `spaceDown` held (a
press pans instead), and two or more live entries in `pointers` (the press is
treated as the second finger of a pinch). All three are reachable and all three
present as "a drag on empty canvas does nothing".

## The three rewiring verbs (2026-08-12)

Bypass, splice/extract, and drag-to-modulate. They were built together because
they answer the same complaint: this app had enormous depth (104 blocks, four
living simulations, a rig, calibration, tape) and a thin set of **verbs**.
Each of these applies to every block rather than adding a 105th, and each is
used many times in a session.

Two rules govern all three, and both came from the user directly:

1. **Nothing may change without announcing itself.** In a dense patch an
   automatic rewire is invisible the moment it finishes, so every one of them
   is *drawn as a proposal before it commits* and *plays a run along the route
   afterwards* (`ui/rewire.ts`).
2. **Nothing may disturb the way things already work.** A splice must never
   fire on a drag that only meant to move a block; a modulator drop must never
   beat a real port; extraction takes a modifier because dragging a block out of
   a chain already means "move it, keep it wired".

### Bypass (`Block.bypass`, `Editor.toggleBypass`, `Renderer.drawBypass`)

Right-click → **Bypass**, or **Ctrl+B**, on the whole selection. Offered only
where `canBypass` holds — at least one audio in *and* one audio out on the
instance's ports. A source, a sink or a MIDI-only block has no path to pass
through, and an item that silenced them instead would be worse than no item.

**It sits at the TOP level of the block menu, not under `Block ▸`.** The rule
this menu is built on is *group what you visit, not what you use*, and A/B-ing
whether an effect earns its place is the most-used verb there is — the same
reasoning that pulled the CV and MIDI items back up out of a submenu.

**What bypass means: "as if the block were not there", latency included.** The
kernel stops running, and whatever latency it contributed goes away with it —
exactly what deleting it would do. That is a deliberate choice and it is the
honest one *for this app*: there is no automatic delay compensation anywhere
here, so a bypass that preserved latency would be inventing a behaviour nothing
else has. The cost, stated so it is not rediscovered as a bug: bypassing a
`conv`, a calibrated `speaker-rig` or a `vst` shifts that branch earlier by a
hop, and a parallel branch through a similar block will no longer line up.

The **visual is the mechanism, not a badge**: the face drains to the canvas
ground and a jumper runs across the block from its audio input to its audio
output, so the signal is drawn going *past* it. The title band is deliberately
left undrained — the same call proximity focus makes, because whatever else is
dimmed a block still has to say what it is (visual-standard B1). It holds still:
bypass is a *state*, not an event, so unlike fault heat it does not animate and
costs an idle canvas nothing.

The engine side (`__bypass`, the cross-fade, the pairing, and why the dry path
*writes* rather than blending) is in [`02-core-ir.md`](02-core-ir.md) and
[`05-native-engine.md`](05-native-engine.md). Covered by
`scripts/bypass-exec-test.cjs`.

### Splice — drop a block on a wire (`Editor.spliceTargetFor` / `doSplice`)

`A → B` becomes `A → block → B`. The existing wire is **re-pointed, not deleted
and recreated**, so its id, its bundle membership and its branches all survive;
deleting it would cascade to every branch on that trunk, which is a far bigger
edit than the one being asked for.

The eligibility test is the entire feature, because the gesture it shares a
shape with is *moving a block*. All five must hold:

1. exactly one block is moving (a group drag is arranging, and there would be
   no answer to *which* one goes in);
2. the block has a **free** in and a **free** out of that wire's kind — an
   already-wired block belongs to the patch somewhere else, and ports are
   single-link anyway;
3. the wire passes through the block's **middle** — `min(w,h)/2`, capped at 90
   — not merely overlapping its rect. You have to put the block *on* the cable.
   (`tryCassetteInsert` can be looser because a lone cassette dropped on a deck
   has no other plausible meaning; a gain dropped near a wire absolutely does.)
4. the wire is not already attached to that block;
5. the wire is a plain wire, not a branch — a branch's `a` end is its trunk
   rather than a port, so there is nothing to re-point.

**The proposal is drawn while the block is still in the air**: the target cable
thickens, two dashed lines show the detour into the block's ports, and a break
mark sits **across** the cable at the cut. The ticks are perpendicular for a
specific reason — drop a block squarely on a straight horizontal cable, which is
the case this feature exists for, and the two dashed detour lines land collinear
with the wire and with each other, rendering as a cable that simply runs into the
block's ports. Indistinguishable from an edit that already happened, which
defeats the point of showing it first.

**The proposal paints above the block pass, not with the wires.** Its cut point
lies *inside* the dragged block by construction, so painted with the cables it is
drawn perfectly and then covered up — which looks exactly like not drawing it.

#### …including straight out of the Library (`previewLibrarySplice`)

A tile dragged out of the Library onto a wire splices in exactly like a block
already on the canvas, because it is the same gesture and a block's origin is
not something the canvas should care about. The only thing missing before the
drop is a block — nothing with a position, a size or ports — so the preview
tests a correctly-sized stand-in, `libraryGhostBlock`, built from the same key
prefixes (`cassette:` / `roll:` / `vst:` / `custom:`) that `addBlockAt`
understands. A preview built on a nominal size would light up over wires the
drop then refused, which is worse than not previewing at all.

Two implementation notes that are easy to get wrong:

- **The key is held in a module value** (`setLibraryDrag`), because Chromium
  blocks `dataTransfer.getData` during `dragover` — mid-drag you can read the
  *types* but not the payload, and the drop is the first moment the key is
  legible from the event. Set on `dragstart`, cleared on `dragend`, and set and
  cleared identically by the touch drag.
- **Both drag paths land in `dropLibraryKey`**, which places and then asks the
  editor to run the same test its preview ran. That shared exit is the reason
  mouse and touch insert identically — HTML5 drag-and-drop is mouse-only in
  Chromium, so touch has its own pointer-event drag and would otherwise have
  quietly lacked the feature.

### Extract — pull a block out and heal (`chainHealFor` / `doExtract`)

Right-click → **Pull out of chain**, offered only when the answer is
unambiguous: exactly one wire in and one out, of the same kind, neither a branch
and neither a trunk with branches on it. "Bridge the gap" has no single meaning
on a block with two inputs, and a guess there silently re-plumbs a patch.

From the menu the block **stays where it is, merely unwired** — not moved, not
deleted. This is the inverse of *inserting an existing block*, so the inverse
leaves you holding that block.

**Alt+drag is the same edit as one motion**: it extracts and then carries the
block off under the pointer, which is what you were going to do next anyway.
One undo entry covers both, taken before the heal, so `Ctrl+Z` puts the block
back in the chain *and* back where it stood.

**A plain drag is still never this.** Dragging a wired block means "move it,
keep it wired", and re-teaching that gesture would break the thing every
existing patch was built with — so the modifier is the whole point, and it is
checked before the face widgets and the dynamic-block artwork: a press with Alt
down is a statement about the entire gesture, and holding it over a knob does
not mean turn the knob. Alt was the one free modifier on the canvas (Shift is
add-to-selection and fine drag; Ctrl is the command modifier).

**The menu item carries `Alt+drag` as its shortcut label.** A gesture nothing
announces is a gesture for whoever wrote it; the menu is where this one is
found. Touch has no Alt — the menu item is the whole vocabulary there, listed in
docs/14's known gaps.

### Drag a modulator onto a knob (`modulateTargetAt` / `tryModulateDrop`)

Drag a cable out of a CV-capable output and drop it on the **widget**. It
creates the `cv:<param>` port and wires it — the port is an implementation
detail of "this knob takes CV" and you should not have to conjure it first.

Eligibility reuses the *same* gate as the `Add CV input` menu item
(`cvableWidget`), because "can this parameter be modulated" must have exactly
one answer in this app — the same principle as the virus's habitat (README rule
17). Refused: the source end of a cable (a knob does not emit), a drop on the
block the cable already comes from, and anything with a real port under the
pointer, which wins. A mirrored widget on a custom block targets the child's
param (`cv:<child>:<param>`), exactly as the menu does.

The preview ring and the drop call **the same resolver**, so what you see and
what you get cannot drift apart.

> **A branch has no far end of its own** (fixed 2026-08-13). Its `a` end roots
> on the trunk rather than on a port (docs/02), so reading the source straight
> off the wire found nothing and the whole gesture silently did nothing —
> dropping a *branched* cable on a knob was inert while dropping it on a port
> worked fine, which is a hard thing to describe as a bug and an easy thing to
> assume is your own mistake. `canConnect` and `fieldLatchAt` already resolve a
> branch's source from the **net**; `modulateTargetAt` is the third drop target
> in this file and was the one never taught the same trick. If you add a fourth,
> it needs the net fallback too.

**The ring traces the control, not the layout item** (`widgetMarkShape`,
`widgetBox`). It used to be a fixed 15 px circle at the centre of the face item,
which is wrong twice: the item reserves a strip underneath for the label, the
value and (sometimes) the silkscreen mark, so its centre sits *below* the dial;
and 15 px is the right size for no widget in particular — a large knob wore a
ring inside itself, a fader wore a small circle in its middle. Reported as "the
indicator is not aligned properly… it also needs to change for the size and
control style".

Three rules fall out of that, and they are the reason the geometry is shared
rather than re-derived:

- **The shape comes from the widget's own painter.** `knobGeom` is called by
  both `paintWidget` and `widgetMarkShape`, so the dial and the ring around it
  cannot drift.
- **It is keyed off the *effective* kind** (`controlOf`), not `spec.widget`: a
  param swapped to a fader in Appearance is ringed as a fader — a rounded rect
  round its track — and swapped back, as a circle.
- **It uses the mark-carved box** (`widgetBox`, exported from `facepaint.ts`
  for exactly this), or on the blocks that print a panel mark it would sit a
  strip's height low.

### The run afterwards (`src/ui/rewire.ts`)

One primitive for all three: a pulse travels **along the route that changed**,
in signal order, ringing the block or widget it arrives at. Deliberately the
route rather than a flash on the changed thing — a flash says "something
happened here", a run says what the signal now does, which is the question you
were actually asking.

It follows the `src/ui/visuals/` contract exactly: one clock tick per
`Renderer.draw`, never its own rAF loop, `rewireAnimating()` turned into
`dirty`, and it holds no document state — runs are keyed by wire id and pruned
the moment those wires stop existing, so an undo or a scene load cannot strand
one.

## Four more verbs (2026-08-12)

The same filter as the three above: things done many times a session, applying
to every block rather than adding another one.

### Fine drag and reset on value widgets

A relative value drag is `travel / 140` — 140 px covers a parameter's **whole
range**, which on a log-curve frequency knob is the entire audible spectrum.
Landing on a specific value with a mouse was not possible, and there was no
reset of any kind in the app.

- **Shift gears the span up by `FINE_DRAG_SPAN` (8)**, so a full sweep becomes
  1120 px. Named as a *span multiplier*, deliberately: written the other way
  round (`span = 140 * 1/8`) it makes the drag eight times **coarser**, which
  still looks like a working fine mode until it is measured. It shipped that way
  for ten minutes and the harness caught it.
- **Changing gear mid-drag re-baselines, it does not jump.** Both the anchor
  value and the anchor position are re-taken at the moment the modifier changes.
  Same rule as a third finger landing in `TwoPointerGesture` (docs/14 rule 1).
  Measured: 0.0000 of jump across the switch.
- **Double-click resets to `spec.def`**, plus a `Reset <name>` item next to
  `Set <name>…`. The gesture was free — `doubleClick` already returned early
  over a widget so a fast note-button tap could not open the rename dialog, so
  the event was being deliberately discarded. Only the relative-drag widgets
  (knob/fader/hfader): a `button` is momentary and a `toggle`/`select` commits
  on the press, so "its default" is not what a second tap is reaching for.

**Touch has no fine mode.** Shift needs a keyboard. Listed in docs/14's known
gaps rather than solved by inventing a gesture — two fingers already mean pan
and supersede the one-finger interaction (rule 8), and long-press is the context
menu, which docs/14 explicitly protects *on knobs*.

### Group parameter edit

Dragging a widget on a block that is part of a multi-selection moves the same
parameter on every selected block that has one. This is the entry on this list
that comes from what LivePatch **is** rather than from patcher convention: a
surround patch is full of parallel things — eight speaker gains, a bank of
delays — and there was no way to move them together at all.

- **Only when the grabbed block is itself selected, in a selection of 2+.** A
  knob on an unselected block behaves exactly as before, byte for byte.
- **Matched by param id, applied in NORMALIZED space**, each peer against its
  own baseline. Two blocks can give one id different ranges (a −60…+12 dB gain,
  a 0..1 level), so a raw delta means something different on each; a normalized
  delta means "move each by the same fraction of its own range". Verified: four
  gains 12 dB apart moved by an identical 4.538 dB each, spread 12.000 →
  12.000, and a peer pinned at its rail did **not** drag the others to theirs.
- **Mirrored child widgets (`link:`) are excluded** — resolving "the same
  parameter" across five other blocks' children is a guess that edits things you
  cannot see.

### Quick add — the canvas arms the Library (`ui/placement.ts`)

Placing a block meant leaving the canvas for the Library, finding the tile and
dragging it back. That is the right tool for *browsing* and a poor one for the
dominant case: knowing what you want and wanting it **here**.

**This was built twice, and the first version was wrong.** It was a bespoke
searchable popup at the pointer. It worked, and it was a mistake: the Library is
already the block browser, with faithful thumbnails, port-type chips,
pinned/recent, hover cards and keyboard navigation — the popup was a worse
version of all five that additionally had to be kept in step with `usableDefs`
(which hides blocks with no unit on Android) and with the Library's own idea of
what matches a query. Two surfaces answering one question is precisely the drift
[`14-input.md`](14-input.md) exists to prevent for gestures.

So the canvas does not open a picker. It **arms an intent** and the Library
serves it:

```ts
armPlacement({ at, hint, snap, onPlaced })   // ui/placement.ts — synchronous
revealLibraryForPlacement()                  // panels.ts — shows + focuses it
```

The state lives in its own tiny module, and that is not tidiness. `editor.ts`
reaches `panels.ts` only through a dynamic import (they would otherwise be a
static cycle), and **both arming and cancelling have to happen in the same tick
as the gesture**. Arming inside the import's `.then` left one microtask in which
the intent did not exist, so a cancel arriving in that window found nothing
pending, did nothing, and the intent then armed itself: a mode the user had
already dismissed, switching itself on.

Three gestures arm one:

- **`Ctrl+K`** (and `Search blocks…`, the first item of the empty-canvas menu,
  which is how it gets found) — reveals the Library, focuses its search, and the
  next block placed lands **at the pointer** rather than at the view centre. It
  is wired from the selection when that is unambiguous: exactly one block
  selected, with a free output matching a free input. Two selected blocks have
  no single answer to "which one feeds it", so nothing is wired.
- **A cable dropped on empty canvas** — offers to finish the cable. Checked
  **last** in `pointerUp`, after every existing drop target, so it can only
  follow a drop that would have left the cable in mid-air.
- **Clicking a loose cable end** — the same offer, on demand. Without it the
  offer is a one-shot: dismiss it and the only way back is to drag a cable you
  had already positioned. A press on an end that was already loose defers both
  its history entry and its meaning until the pointer moves — moved, it is a
  drag; still, it is a selection (`pick` on the drag state).

Four things make this safe rather than a hidden mode:

1. **The intent is consumed inside `addBlockAt`**, the one point every placement
   route funnels through — so Enter, a double-click, the tile menu and a
   drag-out all complete it, rather than only whichever one got wired up.
2. **It is visible and cancellable.** The Library shows a banner saying what it
   is waiting for, with a ✕; Escape in the search box cancels the *placement*
   before it clears the query (the outer mode leaves first); and **any press on
   the canvas** cancels it, because doing something else is how a person says
   "not that".
3. **An armed intent never filters the Library.** It did once — a cable being
   extended hid every block without a matching free port — and that is the wrong
   trade in both directions: it removes most of a browser the user opened on
   purpose, and it does so on account of a mode they may not have noticed. Only
   their own search and filter chips may remove entries.
4. **Offering is not connecting** (`END_SNAP`, `snapsToEnd`). The cable joins the
   new block only if the block lands **on the end** — within 48 px of its rect.
   Connecting regardless is what made a wire end impossible to simply *put*
   somewhere: any block placed afterwards, anywhere, dragged the end to itself.
   The rule is drawn while it applies: a dashed ring of exactly that radius sits
   on the waiting end (`Overlay.awaitingEnd`) and closes up solid while a tile is
   dragged inside it.

Dismissing still costs nothing: the cable stays floating exactly where it was let
go, no wire created and none destroyed.

It is **not** a replacement for the canvas block menu. That menu is
pinned/recent — a handful you place constantly, reachable without typing.

## Context menus on the canvas (`Editor.contextMenu`, `Editor.addBlockMenu`)

`showContextMenu` has **no real submenus** — a `"▸"` item reopens the menu at
the same anchor with a different list. Both canvas menus are built on that, the
same way the Dock's are (`widgetdock.ts`), and the anchor is captured once per
open so a sub-list lands where its parent was.

- **On a block/widget**, in order: the widget under the cursor **flat** —
  `Set <param>…`, the styling sub-lists (`Control ▸` kind swap, `Style ▸`
  variant, `Appearance ▸` label/colour/readouts/opacity, `Range ▸` for an XY
  pad), then CV add/remove, MIDI learn, Add to Dock / Dock all, and parent-block
  mirroring. Then `Face ▸` (text/image items, hidden widgets, reset layout,
  copy/paste face style, edit layout), `Arrange ▸` (align/distribute, block-edit
  multi-selection only), `Block ▸` (rename, enter, size, expose, custom-block
  save), the clipboard/grouping actions, then Rename / Enter / Delete.

  **Only styling nests.** Wiring a CV port, learning a MIDI control and docking
  a widget are things you do *while patching*, so they stay one click away; a
  `Widget: <name> ▸` level over them was tried and put the most-used items two
  clicks deep. The sub-lists that remain are a styling session, not a patching
  move. (The starting point was one flat column of 25+ items where nothing was
  where you looked — the balance is "group what you visit, not what you use".)
  Widget styling here writes `block.controls` — a Dock clone's styling stays
  separate (invariant 13).
- **On empty canvas:** Undo/Redo, the Library's **pinned** entries (recents as
  the fallback), `All blocks ▸`, Select all, Zoom to fit, and Leave subpatch.
  It used to be the entire palette — browsing blocks is the Library's job, and
  the palette is still one item away.

## Proximity focus (`Renderer.focusOf`, `theme.proximityFocus`)

Blocks away from the pointer draw as title + outline and fill back in as it
approaches (`proximityRadius`, `proximityFloor` in Appearance → Proximity
focus). A big patch is mostly meters and knobs you are not looking at.

**It is a paint weight only.** Geometry, ports, wires and hit-testing never see
it, so nothing moves and nothing changes what is clickable — and it cannot hide
something you then click by mistake, because reaching a block with the pointer
is what wakes it. Selected blocks and block-edit mode opt out; `overlay.pointer
=== null` (touch, keyboard, pointer off-canvas) shows everything. No animation
loop: focus is a pure function of the current pointer position, so it repaints
on the existing pointermove invalidation and idles at zero CPU. A far block also
skips its live visual, which is a bonus, not a contract.

## Live visuals (`src/ui/visuals/`, 2026-08-05) — optional, and deletable

An animated layer over the finished picture: four features that use telemetry
the engines already publish to say things the static canvas cannot.

| module | what it draws | fed by |
|---|---|---|
| `flow.ts` | **one system per signal kind** — marching dashes on audio/MIDI, sprockets on tape at the deck's real transport rate, a travelling waveform on CV | port directions, `runtime.transportFor`, the source block's own params |
| `rigface.ts` | the scene's **real speaker layout inside a rig-aware XY pad**, plus a ~2 s fading trail of the source | `doc.scene.rig`, post-CV `modValueFor` |
| `focus.ts` | upstream/downstream tint from the hovered (or selected) block, unrelated blocks and wires scrimmed, downstream **hazed by accumulated latency** | the net index, `vstInfoFor().latency` |
| `faults.ts` | **clip / non-finite / fold / truncation** flashes on the offending block, cooling over ~2.2 s | wire levels, `__folded` on the mods stream |

**Everything is behind `visuals()`** (localStorage `livepatch.visuals`), and the
controls live in **Appearance → Live visuals** (`buildLiveVisuals` in
`panels.ts`). They started in the Options menu and moved on 2026-08-05: these
settings are *how the canvas looks*, which is Appearance's whole subject, and
the "but they are stored outside the Theme" objection does not send them
elsewhere — Appearance already hosts **UI scale**, which is likewise an app
preference rather than part of the scene. The amplitude slider is also what
settled it: a continuous range wants a real slider, not a menu item.

Two notes for anyone editing that section:

- **It repaints via `ed.renderer.invalidate()`, not `doc.touch()`.** These
  settings are not in the document, so a `touch` would not mark an idle canvas
  dirty and the change would not appear until something else moved.
- **The slider must not trigger the panel rebuild.** Discrete toggles call
  `rebuild()` so dependent rows update their disabled state; the slider only
  calls `invalidate()`, because rebuilding would recreate the slider element
  under the user's cursor mid-drag. It drags through the shared `dragHandle`
  for the same reason UI scale does — a native range remaps the pointer onto
  its own geometry, which slams the value to one end when the panel relayouts.

**`flow: false` is offered as a named choice, `Cables: classic`, not as an
unchecked box** — it restores the original cable appearance down to the last
pixel, including CV level-as-thickness, and preferring that is a real position
somebody can hold rather than merely the feature being off. It is deliberately **not** in `Theme`: a
Theme belongs to the Scene, and this is an installation preference — the same
line `core/prefs.ts` draws — which also means deleting the folder leaves no
dead field in every saved scene.

**The removal recipe**, because "easy to drop" was a requirement and a
requirement nobody wrote down is not one:

1. Delete `src/ui/visuals/`.
2. Delete the lines marked `LIVE VISUALS` in `render.ts` (import, three in

Nothing else imports from the folder and nothing in it is load-bearing for
correctness — every entry point is additive paint over a picture that is
already complete.

Four things it holds itself to:

- **It rides the app's one rAF loop** (rule 9 of docs/10). Animation advances
  in `visualsFrame()`, called once at the top of `Renderer.draw`; anything
  still moving calls `requestVisualsFrame()`, and `draw` turns that into
  `dirty`. Without that last step a flash would freeze half-cooled the instant
  audio stopped — the frame loop only runs on `dirty || audioOn`.
- **Elapsed seconds, never frame counts.** The render loop is on-demand, so
  frames arrive at 60 Hz with audio on and at whatever the pointer produces
  without it. A per-frame increment would make a drifting CV band speed up and
  slow down with the app's workload, which reads as a fault.
- **It invents no telemetry.** Every animated quantity is a number the system
  already knows. Where no such number exists the thing is not drawn: **MIDI
  wires get direction but no per-event pulses**, because nothing reports
  per-wire MIDI activity to the renderer (`wireLevel` is an audio analyser
  reading and returns null for a midi net; `midi-seen` fires only while
  MIDI-learn is armed). The same reasoning excludes the most precise fault
  signal in the app: each kernel's `trapNonFinite` **purge count**, which lives
  on the audio callback where golden rule 1 forbids messaging. `faults.ts`
  catches the same event from outside — a non-finite reading reaching the level
  analyser — which is strictly less information (it cannot name the kernel that
  purged) and costs nothing.

### The CV cable, and three ways of getting it wrong (2026-08-05)

Worth reading before touching `flow.ts`, because each attempt looked correct
and each shipped an artefact the user named precisely:

1. **Thickness from level** — the behaviour the app shipped with, and still has
   under `Cables: classic`. A cable visibly breathing 60 times a second:
   *"useless and janky past 5 Hz"*. Geometry that chases a waveform stops
   resolving above a few Hz and smears; worse, it re-pitched everything drawn
   on top of it, so a dash band riding the cable squashed and stretched as the
   level moved.
2. **Dash speed from `|Δrms|/dt`** — a steady source has a steady rms, so an
   oscillator patched to a CV input read as *stationary* after its opening
   transient, and the derivative of a ~20 Hz metered value is mostly its own
   noise: *"fast for a second, then drags down before snapping back"*.
3. **Dash speed from the crest factor** — stable, but it cannot separate
   0.1 Hz from 10 Hz. It says only *whether* a line varies.

All three tried to infer a control's behaviour from the cable's level meter,
which does not contain it. **The behaviour is declared on the source block**,
exactly and for free — `vco` has `freq` + `shape` (saw→pulse) + `pw`, `lfo` has
`rate` + `shape` (tri→square) + `amp`, `osc` has a `wave` enum, `wavegen`
carries the waveform the user drew, `sh`/`random` declare hold vs smooth. So
the cable draws the source's own waveform: **wavelength from frequency,
amplitude from strength, shape from what it declares.** `vco`, `lfo` and
`env-adsr` publish their rate through `liveParams()` so a frequency-modulated
oscillator's stripes track the modulation; `osc` and `wavegen` publish nothing
and their param is read from the document — exact, but not CV-aware, which is a
stated limitation rather than a papered-over one.

Four rules fall out, and breaking any of them reproduces one of the artefacts:

- **Nothing drawn on a cable may take a length from a per-frame value.** Only
  phase and alpha may move at frame rate. Wavelength changes when you turn a
  frequency knob, which is feedback; dash length changing with level is the
  squashing.
- **Wavelength is clamped, and its range is spent on LFO rates** (0.05–20 Hz,
  `WL_MIN`/`WL_MAX`). Spanning the whole audible band instead compressed
  everything anyone actually watches — 1 Hz and 4 Hz landed a few pixels apart
  and read as the same cable, reported as *"the frequency doesn't even
  match"*. The bottom clamp stops 0.05 Hz reading as a straight line,
  indistinguishable from nothing happening; the top clamp matters more,
  because a wavelength approaching the polyline's own sample spacing aliases
  and strobes backwards.
- **Travel is the source's real frequency in cycles per second, capped at
  `MAX_VISIBLE_HZ` (12).** This is the half that makes the picture *match*
  rather than merely correlate: fix your eye on one point of the cable and it
  bobs at the rate the oscillator is running — 1 Hz gives one crest a second,
  4 Hz gives four. Travel was a constant at first, so the wavelength was the
  only cue and two different LFOs moved identically. Above the cap the eye
  stops resolving cycles anyway and the advance per frame would approach half
  a wavelength, which aliases; past 20 Hz the wavelength saturates too, so
  **20 Hz and 440 Hz are deliberately indistinguishable here** — an audio-rate
  CV reads as "audio rate" and no finer.
- **The ripple is the cable's GEOMETRY, not something drawn on it.**
  `cvRipplePoints` hands `drawWire` a displaced polyline and every stroke —
  border, signal colour, selection halo, multichannel core — follows it. The
  first version stroked a pale wave *over* the straight cable and read as two
  objects: *"a faint white wave in front of the original purple"*. Hit-testing
  keeps the straight path on purpose; grabbing a cable must never mean chasing
  a moving curve, and the displacement stays inside the existing grab band.
  The offset tapers to zero at both ends, or the wave visibly detaches the
  wire from the port it is plugged into.
- **A waveform's height is its DECLARED amplitude, never the wire meter.**
  `lfo` has `amp`, every other periodic source has `level`; that param is read
  fresh each frame (`CvShape.strength`), exactly like frequency and shape. The
  first two tries read `levelFor(w.id).peak` instead, and a periodic signal's
  peak *within the analyser window* rises and falls at the signal's own rate,
  so the whole drawn wave breathed once per cycle — worst on a sawtooth, whose
  windowed peak swings hardest (*"the waves are still expanding and
  contracting, sawtooth the most obvious offender"*). A declared param only
  moves when the user turns the knob. This is the same lesson as the frequency
  and shape fixes: the meter cannot describe a control voltage; the source
  block declares everything. A *wandering* value (gate, envelope, knob) is the
  one exception — it has no declared amplitude, so its motion is measured with
  a 1 s peak-to-peak envelope (a periodic source's peak-to-peak would be ~0,
  which is why the two families are separate code).
- **Cache identity, never values.** `cvSourceOf` is keyed on `doc.netRevision`
  and may therefore hold only *which block and which param ids* — because
  `netRevision` deliberately does not move on a `'param'` touch (it keys on
  'structure' and 'selection' so a knob turn does not invalidate the net
  index). The first version cached the resolved waveform, pulse width and
  frequency there too, and all three froze at the moment the wire was drawn:
  switching an oscillator from sine to square did nothing, and raising its
  frequency did nothing. Two separate reports, one mistake. `cvShapeOf` re-reads
  the mutable values every frame.
- **Draw the waveform's VERTICES, not samples of it.** A square sampled twelve
  times a cycle and stroked with round joins is a wobbling blob, and a
  sawtooth loses its flyback entirely. Each shape declares the corners it
  actually has — square/pulse two per cycle with a `before` and an `after` at
  the same position (which is what makes an edge vertical), triangle two,
  sawtooth one with the drop, staircase eight. Fewer points than sampling and
  exactly right rather than approximately. Only sine and a hand-drawn
  `wavegen` waveform are sampled, because they have no corners to preserve.
- **Direction, and branch continuity, both live in one coordinate: `u`,
  distance from the net's source along the flow.** `phase(u) = u/wl − wave`,
  and a wire's own arc position maps in as `u = d0 + (dir === 1 ? d : length −
  d)`. `d0` is the distance already travelled from the source to this wire's
  start (`rootDistance`, which walks the `parentId` chain for a branch), so a
  branch simply *continues* the trunk's `u` — the wave runs through the
  junction as one signal instead of restarting at the branch-root dot. An
  earlier `dir·(d/wl − wave)` form moved the pattern toward larger `d` for both
  path orientations, so on a backwards-drawn wire it ran upstream; expressing
  everything in `u` fixes that too, because increasing `wave` always raises
  `u`, i.e. always moves downstream.
- **The phase clock belongs to the NET, not the wire** (`netWave`, advanced
  once per net per frame). Per-wire phase gave a branch and its trunk
  independent clocks that drifted apart within seconds, so the same signal
  arrived at the junction as two unrelated waves. That was the whole of
  *"it's broken for branched wires"*.
- **Flexing leads, never an amplitude taper.** The wire must meet its ports at
  zero offset, so *something* bridges the port to the oscillating cable. A
  taper (amplitude → 0 over the last ~18 px) made every crest grow on the way
  in and shrink on the way out — *"a single wave sample shouldn't shrink and
  expand as it travels"*, and it shouldn't: a wave has one amplitude. The
  middle now oscillates at full constant height and a short straight **lead**
  at each end connects the port to the wave's interpolated value at that
  boundary (`valueAt`, so the attachment slides continuously instead of
  popping vertex to vertex). The cable flexes at the plug like a real patch
  lead; no crest ever changes size. Verified in Node: interior peak is
  invariant across all phases, and the value at a branch junction equals the
  trunk's there exactly.
- **A non-periodic source draws a flat line displaced by its value.** A gate
  sits high or shut low in the control colour, an envelope's cable rises and
  falls bodily, a parked knob is dead flat. This is not a fallback — a sine on
  a gate is a lie about the signal, and two straight lines are more legible
  than any ripple. It is also what makes a still patch completely still, since
  amplitude is strength: visual noise ends up proportional to activity.

**One system per kind, never a shared layer plus extras.** CV draws its
waveform and no dashes; tape draws sprockets and no dashes. Two moving patterns
at two speeds on one cable read as interference rather than as two facts.
- **It never paints from inside `drawBlock`.** That function writes
  `globalAlpha` per face item and resets it to 1 after the item loop, so an
  alpha set by a caller is silently discarded partway through — the same trap
  the LED meter styles document above. The focus scrim and the fault heat are
  therefore passes *over* the finished blocks, tracing `traceBlockShape`
  themselves.

**The latency model is small and entirely real** (`latencyOf` in `focus.ts`).
`conv` and a *calibrated* `speaker-rig` cost `hopFor(sr)` samples — the engine's
own hop formula, reproduced with a pointer back to `engine/src/dsp.ts` and
driven by the same live sample rate `setEqDisplayRate` feeds the EQ curves; a
`vst` costs whatever the plugin reported through `vst-info`. Everything else
contributes **zero rather than a plausible guess**, and a Delay's delay is
deliberately not counted — that is the block doing its job, not latency the
patch is paying without asking. Measured on a Panner → Conv → Speaker Rig
chain at 48 kHz: 256 samples, i.e. the ~5.3 ms one hop that
[`10-performance.md`](10-performance.md) describes as ~1.7 m of path
difference when it lands on only part of a rig.

The traversal takes **shortest depth but longest latency**, and relaxes: depth
answers "how near is this to what I am pointing at", so the short route is
honest, but if a signal reaches a block by two routes of different delay the
block hears the later one too, and quoting the shorter would understate exactly
the misalignment the feature exists to show. A diamond — one source split
across a corrected and an uncorrected branch — is the normal shape here, not
an edge case, so a single sweep would be wrong in the common case. The relax
queue is bounded (`RELAX_MAX`) because a patched feedback loop is legal.

## Widgets (`src/ui/widgets.ts`)

Pure painting + value math + **shared hit geometry** (so the renderer and the
editor agree exactly). Value mapping: `val2norm`/`norm2val` honor `min`/`max`,
`curve: 'log'`, `step`/`int`. `paintWidget(g, rect, spec, value, theme, hot, v2,
mod, mod2, variant, cs)` handles knob/fader/hfader/xy/toggle/button/select;
special painters: `drawKeys`, `drawWave`, `drawSampleView`, the EQ curve math.
Gate-CV lights up buttons/toggles when `mod === 1` — in **every** variant.

**The `keys` widget has two layouts, and one geometry function.** `keyLayout(r,
octave, variant)` is the only place either is described: default is a piano
(as many ~15 px white keys as the box holds), `variant: 'pad'` is **one octave
of rounded buttons in two rows** — the layout small semi-modulars print instead
of keys, and what the Mavis's 13 buttons are. The count is fixed rather than
derived from the width because these are buttons: a wider panel is meant to
produce bigger buttons, not more of them. `KeyLayout` therefore carries a
`whiteY`/`blackY` per row (equal on a piano, where the black keys overlay the
white ones), and `keyAt` reads them — hit geometry and painting cannot drift
(invariant 2).

**A mirrored keyboard plays the child, not the host (2026-07-31).** `keys` used
to bail out of `Editor.widgetDown` whenever the ref resolved to a child
("keys don't mirror to parents"), because every line in the drag path was
written against the host block: `pressedKeys.get(b.id)` and
`runtime.nodeId(b.id)`. On a custom block that is the wrong node and the wrong
held-note set, so a keyboard exposed on a panel drew but did nothing — while the
identical widget in the Dock, which had always resolved through `ResolvedRef`,
played fine. The drag state now carries `target` (the block that owns the
keyboard) and the `nodeId` resolved at press-time, and the exclusion is gone.
`keyboard` and `midi-trigger` are marked `isControl`, so "Show on parent block"
offers them at all.

**Per-control styling** (`ControlStyle`, keyed on `block.controls[ref]`): the
knob↔fader `kind` swap, a paint `variant` (knob `arc|needle|ring`, fader
`track|slim|led`, toggle `switch|check|led|rocker|power`, button
`rect|pill|round|flat`, **keys `piano|pad`**), plus `label` (display-name
override), `color` (accent override), `showLabel`/`showValue` (hide the
name/readout), `showMark` (hide the printed panel symbol, below) and
`onLabel`/`offLabel` captions (rocker halves, pressed buttons). All editable in
Properties → Controls. `controlOf` passes the variant through for *any* widget;
only the swappable kinds may change widget.

**A variant that is not in the menu tables does not exist to the user.** The
`keys` widget had `piano`/`pad` from the day the Mavis shipped and no way to
choose between them: it is not a swappable kind, so `Control ▸` never offered
it, and it had no entry in `VARIANTS` (`editor.ts`) or `variantsFor`
(`widgetdock.ts`), so `Style ▸` was hidden too. The layout was reachable only by
hand-writing `controls` in factory code. **Both tables are part of adding a
variant** — they are deliberately duplicated (the Dock styles clones
independently, invariant 13) and therefore both have to be edited.

**XY pads go through `xyAxes` (2026-07-25).** A pad used to be hard-wired to
0…1: the painter read the raw parameter as a normalized figure and the drag
wrote the normalized figure straight back. Every pad whose parameters are not
0…1 was therefore broken — a Panner 3D's X runs −1…+1, so its centre drew hard
against the left edge and a drag could only ever reach the front-right quadrant
(`px = nx * R` in the kernel). `xyAxes(params, spec, lookup)` resolves both
axes' effective specs and everything maps through `val2norm`/`norm2val`, which
also puts **0 in the middle** of any symmetric range and draws the zero lines.
A block may carry `<id>Min`/`<id>Max` params to make its own range editable (the
XY Pad control does, per axis); a reversed or degenerate pair is ignored rather
than producing an un-draggable pad. Four call sites must agree: `facepaint.ts`,
`thumbnail.ts`, `Editor.applyXY`, and the Dock's `applyXY`.

The `sampleview` widget (Ableton-style waveform region editor) is the pattern to
follow for a new interactive widget: exported geometry (`sampleHandleAt`) shared
between painter and editor, driving sibling params via `linkParams`
(`start`/`end`/`fadein`/`fadeout`), all plain floats so they're CV-modulatable.
The `eq` visual is the same pattern for a visual (`eqPlotRect`/`eqFreqToX`/…).
Its full model lives in `widgets.ts` (`eqBand`/`eqCoeffs`/`eqResponseDbBus`/
`eqBandHandles`): `eq-curve` is a 16-slot parametric EQ (fixed slots keep every
band param a static CV target — bands are *enabled/disabled*, never added as
params), any RBJ filter type, routed per-band to bus A/B/both, where `mode`
(Stereo / Mid-Side / Left-Right) sets what A/B mean. The block face, the face
drag (`editor.ts`), and the Advanced deep editor (`adveq.ts`) all consume that
one module, so they can never disagree.

**The curve is drawn at the engine's real sample rate (2026-07-30).** The rule
"the drawn curve *is* the audio" needs one more thing than a shared formula: the
same `fs`. `EQ_FS` used to be `const … = 48000`, so every curve in the app —
face, face-drag handles, deep editor — described a 48 kHz filter no matter what
the engine was running. That is not a uniform offset: a biquad's response is a
function of `f/fs`, and the bilinear transform's warping is concentrated near
Nyquist, so at 96 kHz a 16 kHz bell is genuinely narrower and better centred than
the 48 kHz picture claims, while the low end is untouched. The picture disagreed
with the audio exactly where users look hardest.

`EQ_FS` is now module state fed by `setEqDisplayRate`, called from
`updateStatus()` in `shell.ts` — the one function every engine and status change
already funnels through. It reads `runtime.native.status.sampleRate` on the
native engine and `runtime.webaudio.ctx.sampleRate` on the web one, and ignores
implausible values so a half-initialised status message cannot blank every curve.
Curves repaint on the app's rAF loop, so nothing else needs to know.
`scripts/samplerate-test.cjs` asserts the *kernel's* measured magnitude matches
the RBJ model at the running rate, which is the other half of the same promise.

### The Advanced tab and its first editor (`adveq.ts`)

Dock tab 3 (`advanced.ts`) is a registry (`registerAdvancedView`); the EQ Curve
editor is the first real one and the reference to copy. Two gotchas it paid for:

- **Display is owned by `.adv-view` / `.adv-view.on`.** A view's root styling
  must not set `display` on an equal-specificity class — a bare `.adveq{display:
  flex}` overrides `.adv-view{display:none}` (later, same specificity) and the
  editor never hides on deselect. Scope it to `.adv-view.adveq.on`.
- **Param ticks call the tab's `repaint`, falling back to `refresh`.** The
  Advanced tab now implements `repaint` to just refresh the active editor's
  values (cheap) instead of re-evaluating candidates and rebuilding DOM under the
  cursor. A deep editor's own `setTarget`/`refresh` must likewise be cheap and
  idempotent (rebuild its inner DOM only when the target block or selection
  changes) because `advanced.ts` calls them on every selection/param update.

- **`setTarget(null)` means "you have lost your block", and the tab must send
  it.** A deep editor may be holding state *on* the block it was pointed at —
  the EQ's Flat compare parks `mix` at 0 while engaged — and only that call
  tells it to put the state back. `advanced.ts` used to just hide the view when
  the selection had no candidate, which left the EQ silently dry with nothing on
  screen to explain it.

**The EQ's A/B and Flat (2026-07-25).** `⇩A`/`⇧A`/`⇩B`/`⇧B` store and recall
whole settings (`snapA`/`snapB` params). A recall is a **swap** — the settings
you are leaving go into the other slot — which is what makes it a comparison
rather than a one-way restore. Store buttons light when their slot is occupied
and recall buttons are *disabled* when it is empty; the old `A◄ ►A` glyph pairs
were ambiguous about direction and recalling an empty slot returned silently, so
the feature read as broken either way. **Flat is a comparison, not an eraser:**
it holds the EQ dry (`mix` 0) while engaged and restores the real mix on
release, touching no band parameter. It used to zero every band gain, which
destroyed the curve with undo as the only way back — that destructive flatten
now lives on the plot's right-click menu, labelled as such.

The editor takes its per-frame tick from `AdvancedViewHandle.onFrame` (the app's
single rAF — never its own loop), maps canvas pointer coords through the measured
rect as a *fraction* (UI-scale-safe), writes params straight to
`params`/`runtime.sendParam` like the face drag, and adds CV via `doc.addCvPort`.
The analyzer overlay reuses the spectrum feed: the kernel exposes `visualTime`
and `graph.ts` FFTs watched `eq-curve` nodes (same path as `spectrum`).

## Layout (`src/ui/layout.ts`)

- `autoFace(block)` flows face items: title → param widgets → visual → exposed →
  linked, wrapping at `MAX_ROW_W`. Block-edit mode materializes this into
  `block.layout` for free rearranging; `faceItems` returns the hand-edited
  layout when present, else auto. Hand layouts may also carry `text:<id>`
  (backed by `block.texts`) and `image:<assetId>` items — neither exists in
  auto layouts, and both survive the auto↔hand sync filter.
- **Shape-true clamping**: `clampFaceItem`/`faceItemRoom` clamp against the
  outline's *scanline runs* (`shapeRunsAtY` in geometry.ts). Concave custom
  shapes expose every disjoint run — a U-shape's arms, a star's lobes — as
  usable space (`spansForRect` intersects runs across the item's height;
  `clampXToSpans` picks the run nearest the drag). The old fitted-rect
  fallback only remains for malformed (<3-point) custom shapes.
- `widgetSize` maps each `WidgetKind` to a default face size — **add an entry
  when you add a widget kind** or it defaults to a tiny box.
- `padOf` reserves space for inward-drawn port labels and insets non-rect
  shapes. `syncBlockSize` grows an auto-size block to wrap its face — except
  under `style.freeWidgets`, where the block deliberately holds its size.
- `style.noCollide` skips `fitFaceLayout`'s collision-relax passes (and the
  resize shrink-floor): deliberate overlaps stand; outline clamping remains.
- `controlOf` + `SWAPPABLE_WIDGETS` implement per-item knob↔fader swaps
  (`block.controls`); purely visual, never reaches the IR.

## Face editing (block-edit mode, `E`)

- **Snap guides** (`Editor.snapFaceItem`): dragging an item pulls onto sibling
  edges/centers and the content box (±6 *screen* px, so tolerance follows
  zoom), with dashed guide lines drawn via `overlay.snapGuides` — published
  only for alignments that survive clamping, so guides never lie. A 4 px face
  grid applies first when the theme's snap toggle is on; alignment wins.
  Toggleable via theme `faceSnapGuides` (Appearance → Canvas).
- **Multi-select** (`overlay.editSel`): shift-click toggles items; a drag moves
  the whole selection (each member clamped independently). Right-click offers
  align left/right/top/bottom, center H/V, and distribute H/V (bounding-box
  based, ends pinned).
- **Z-order**: paint order *is* `block.layout` order (hit-testing walks it
  backwards). Bring to front / send to back just splice the array.
- **Per-item `alpha`**: 0 = invisible *and untouchable* in patch mode
  (`tangibleItemAt` filters it); block-edit ghosts it at ≥0.35 so it stays
  grabbable. Sliders per item in Properties → Face items; quick Hide/Fade/Show
  in the context menu.
- **Text items**: `Add text…` on the block menu; double-click a label to edit.
  Font size/color per text in Properties. **Images**: `Add image…` (assets land
  in the shared store, below), `fit: stretch|contain|cover` per item, plus a
  whole-block skin (`style.bgImage`) clipped through `traceBlockShape` — the
  image-as-mask look. Decoded bitmaps come from `src/ui/images.ts`, an async
  cache that never decodes inside `draw()`.
- **Copy/paste face style** (context menu): layout + controls + texts + the
  visual style bits paste onto same-type blocks; style bits alone paste
  cross-type ("Paste block style").
- **Reset layout** returns to `autoFace` but re-places text items and clears
  alphas.

### Silkscreen and relationships on ORDINARY blocks (2026-08-01)

The panel vocabulary below is authored by hand, which is why exactly one block
in the app had any of it. Two `ParamSpec` fields bring it to every block, with
no layout authoring at all:

- **`mark`** — a glyph name from `glyphs.ts` (or any other string, printed as
  small dim text) shown in a strip under the widget. `layout.ts` reserves
  `MARK_H` (13 px) in `itemSize`, so the strip is real space in the flow rather
  than something drawn over the neighbour below, and `paintFaceWidget` carves it
  off *once* and prints it after the widget — every painter under it still sees
  the widget's own box. Because it lives in the shared painter it reaches the
  Dock's clones for free. `ControlStyle.showMark: false` opts a widget out; the
  Mavis sets it on every knob, because that panel prints its own symbols at
  exact coordinates and would otherwise carry two of each.

  **A mark must say something the control's own name does not, and the glyph
  table is not a palette to fill.** The first pass across the library reached
  for whatever was already in `glyphs.ts` and ended up printing the same wedge
  under 37 different knobs and the same knob-travel arc under 12 — a wedge under
  a control already labelled *Level* is decoration, and a strip that says the
  same thing everywhere trains the eye to stop reading it. Three rules came out
  of that:

  1. **No mark on a plain Gain / Level / Volume.** The name is the symbol.
  2. **Write the glyph the action needs**, rather than borrowing the nearest
     one. `glyphs.ts` grew from 17 symbols to ~40 for this: `echo` (a hit and
     its repeats) for a delay time, `feedback` (a loop with an arrow) for a
     regeneration amount, `mix` (the crossfade X), `threshold` (a level line
     with the signal breaking through), `ratio` (the transfer curve bending at
     the knee), `tail` vs `predelay`, `bell` / `shelf-low` / `shelf-high` /
     `bandwidth` for the four things an EQ knob can move, `distance`, `absorb`,
     `air`, `rolloff`, `spread`, `width`, `drive`, `ceiling`, `range`,
     `offset`, `depth`, `tilt`, `glide-up`/`glide-down`.
  3. **Two params may share a glyph only when they ask the same question.**
     `rate` is on seven controls because "how fast" really is one question;
     `distance` covers both a Distance knob and an orbit Radius for the same
     reason. Everything else is one glyph, one meaning.

  A knob that **crossfades between two waveforms prints both of them**
  (`saw-pulse`, `tri-square`), the way the hardware does — printing one would
  claim it is a switch. The mark strip is about 26 × 9 px, so anything round
  (`feedback`, `spin`, `distance`) is drawn as a `SPECIAL` in *rect* space where
  it can take its radius from `min(w, h)`; described in unit coordinates it
  would come out as a very flat ellipse.
- **`affects`** — the params whose *meaning* this one changes. The face draws a
  tie from this widget to each named one (`Renderer.drawParamTies`), **dim while
  the source sits at its default and brightening as it moves away from it**.
  That distinction is the whole feature: a panel of knobs cannot otherwise
  answer "why is turning this one doing nothing?" (because Sync is on, because
  Mix is at zero, because the scale is chromatic).

Three things that keep it cheap and legible:

- `hasTies` memoizes "does this type declare any `affects`" per block type.
  Nearly every block declares none, and `drawBlock` runs for every block on
  every frame while audio is on — a `params.some(...)` scan there is exactly
  what [`10-performance.md`](10-performance.md) is about.
- Ties are drawn **after** the item loop restores `globalAlpha` to 1, with their
  own rgba. Inheriting an item's fade would make a tie vanish because one of its
  two ends happens to be dimmed.
- **A tie is printed artwork, not a wire, and that decides its geometry.** The
  first version drew a quadratic through a control point; on anything but two
  adjacent knobs it bent back over itself and read as a scribble. Real panels
  print relationships as straight runs meeting at right angles, in the gutters
  between controls, so `tieRoute` emits horizontal and vertical segments only,
  softened by `strokeElbow` (which never rounds a corner by more than half of
  either adjoining segment — otherwise the corner overshoots and the line
  visibly doubles back, which is the scribble again). A filled pip marks the
  driving end and an arrowhead the driven one: the relationship has a direction,
  and a bare line between two knobs does not say which of them is in charge.

  Four cases, in the order a draughtsman would pick them:

  | | |
  |---|---|
  | side by side, nothing between | one straight segment along the band the two boxes share |
  | stacked, nothing between | the same, vertically |
  | different rows | a three-segment elbow through **the gutter between those rows** |
  | same row, something between | step out of the row, run back along it, step in |

  The third case is the one that had to be learned twice. Routing "outside both
  boxes" is still orthogonal and still looked like a detour, because it was one:
  a Reverb's Mix→Tone tie went up over the title, along the whole width of the
  panel, and back down. The gutter between the two rows is the one strip
  guaranteed to be free of widgets *and* inside the block. `lane` staggers
  several ties off one control so they read as a small bus rather than one thick
  line, and the "is anything between" test is against **every** face item, not
  just the two ends — missing the widgets in between is the entire job.

Only `param:` refs are tied: a mirrored `link:` would need *both* ends mirrored
onto the same face, and a tie with one end missing is worse than none. Targets
that are not on the face (a `face: false` param) are skipped silently.

### Panel silkscreen (`FaceText` decorations + `src/ui/glyphs.ts`, 2026-07-31)

A hardware front panel does most of its explaining with *printed artwork*: the
sawtooth and the pulse at either end of a WAVE knob, the rising ramp under
ATTACK, the box that groups a section, the reverse-video label that says "this
jack is an output". A block face could do none of that — it had captions and
nothing else — so the Mavis was a correct panel that did not look or read like
one.

It is all `FaceText` now, deliberately **not** a second face-item kind:

| field | draws |
|---|---|
| `bg` | filled rounded box behind the item (reverse-video label) |
| `border` + empty `text` | a section box; with text, an outlined label |
| `radius` / `lineWidth` | corner radius and stroke width for both |
| `rotate: ±90` | quarter turn about the item's centre — vertical section tabs |
| `glyph` | a vector symbol from `src/ui/glyphs.ts` instead of the text |
| `decor` | printed artwork: **not hit-tested in patch mode** |

Reusing the text item is the whole point: placement, clamping, per-item alpha,
z-order, the Properties face-item list, copy/paste face style, undo and
persistence already work on `text:` refs, and a new ref kind would have needed
all of it again (and would have been dropped by `faceItems`' filter until it
was added there too).

`glyphs.ts` holds the symbols as **polylines in a unit box** (y down, canvas
order) rather than a font or an image: no UI font has a sawtooth or a filter
slope, an image asset would live in the user's cassette store — so factory
content could not reference one and deleting it would break the panel — and a
path scales with the block, which is how a panel laid out in fractions of a
resizable box survives being resized. `PANEL_GLYPHS` is exported so factory
content can be checked against it; an unknown name draws *nothing*, silently,
which is exactly the failure class `scripts/factory-preset-test.mjs` exists to
catch.

**`decor` is not cosmetic bookkeeping.** A section box is a quarter of the
panel, and a text item is hit-testable: without it the box was the item found
under every pointer inside it, so dragging the panel grabbed the box instead of
the block and double-clicking anywhere inside offered to edit its (empty) text
instead of opening the custom block. Silkscreen is *printed on* the panel, not
placed on it — `tangibleItemAt` skips it in patch mode, and block-edit mode
still grabs it so it can be moved and restyled.

## Ports on the perimeter

`Port.perim` (0..1 arc length along the drawn outline) is the authoritative
position once set — dragging a port in edit mode writes it via `pointToPerim`,
so ports slide *continuously* around circles/hexes/custom outlines instead of
being quantized to four box edges. `edge`/`t` are kept derived (labels, wire
sides, old-build fallback); editing them in Properties clears `perim`. Wire
exit direction uses `portNormal` — the true outline normal for perimeter
ports, cardinal `edgeNormal` otherwise. Scenes without `perim` behave exactly
as before.

## Panels (`src/ui/panels.ts`)

Four dock panels, all schema-driven:

- **Library** — a block browser (rebuilt 2026-07-21). Header = search + port-type
  filter chips (Audio/CV/MIDI/Tape) + grid/list density toggle + category chips
  (`All`, `Pinned`, then `CAT_ORDER`; `Cassettes` always shown so its Add
  buttons are reachable). Body = sections with sticky headers and subgroup
  subheaders driven by each def's `category`/`group`. **Recent** (auto) and
  **Pinned** sections lead the `All` view. Tiles carry **faithful thumbnails**
  (see below), a pin star, and a delete ✕ (custom/cassette). Drag
  (`text/livepatch-block`), double-click, or keyboard-Enter add via `addBlockAt`
  (`type` / `custom:<key>` / `cassette:<id>`), which also records **recents**.
  Right-click a tile → Add / Pin / (custom: Rename, Delete) / (cassette: Save
  as WAV·MP3·OGG·FLAC via `encodeAudio`+`saveAudioFileAs`, Rename, Delete).
  Cassettes tab has **＋ Add files… / ＋ Add folder…** (folder only when
  `canImportFolders`), and the **Rolls** tab has the same pair for MIDI plus
  **＋ New roll** — rolls are assets in the same sense cassettes are, so
  importing a folder of MIDI is as ordinary as importing a folder of samples.
  **An asset category renders even when it is empty** (`ASSET_CATS`): its action
  bar is the only way to add the first asset, so an early-return on
  `!list.length` hides ＋ Add files… exactly when it is needed. Rolls was
  missing from that exemption and had no reachable Add buttons until one
  existed.
  `Structure & Custom` shows the three builders (subgraph + portals), a divider,
  the rest of the category grouped normally, a divider, then user customs.
  **A category's special case must still render everything in that category.**
  This one listed the builders and the customs explicitly and dropped the
  remainder on the floor, so a block filed here was reachable only by *searching
  for its name* — which is no way to find a block you don't know exists. It hid
  Comment from the day Comment shipped, and then Matrix, and both times the
  block looked like it had failed to register. If a tab needs a bespoke order,
  order the entries; do not enumerate them.
  - A rendered entry with no `group` gets no subheader, so beside a grouped
    sibling it reads as belonging to that sibling's group. Give every entry in a
    mixed category a `group` (this is why `comment` has one, and why the four
    Visual blocks gained `Analysis`/`Levels` when cross-filed monitors started
    landing in that tab).
  - **A block may be filed in more than one place** (`BlockDef.alsoIn`,
    2026-08-01). One home is often a quiz: a Convolution is a time effect *and*
    a room simulator, a VST is hardware *and* an effect, the Speaker Rig is an
    output device *and* the centre of the surround set. A cross-filed entry is
    the same block — same `key`, same drag payload, same pin — rendered on a
    second shelf.
    - Entries therefore carry a **`uid`** as well as a `key`. Everything about
      placing, pinning and dragging keys off `key`; the keyboard cursor and
      `scrollIntoView` key off `uid`, or both tiles of a cross-filed block would
      jump to the first copy.
    - `byKey` (Recent, Pinned, and the canvas menu's lists) is built
      **first-wins**, so a copy can never become what those quote.
    - **Search shows a block once.** A flat list of results has no categories to
      disambiguate, so `dup` entries are filtered out of the search branch;
      browsing shows a block wherever it is filed.
  - **Every custom block is in the Custom tab, always.** Letting the factory
    presets be filed by subject was right — a Mavis belongs beside the
    instruments — but it also took them *out* of the one tab whose entire job is
    "the blocks that are not built in", so Structure & Custom listed the user's
    own saves and implied the shipped ones did not exist. A custom entry whose
    home is elsewhere gets a second entry there.
  - **Thumbnails** (`src/ui/thumbnail.ts`): a *static* mini-renderer that builds
    a transient `Block` from the def and draws it with the same primitives as
    the live canvas (`traceBlockShape`/`faceItems`/`paintWidget`/`portPos`), so
    tiles match the workspace. Results are cached in an offscreen canvas keyed by
    a theme fingerprint + size + entry key, then blitted — a full Library
    rebuild (every keystroke) is just `drawImage`s. It is NOT the render hot
    path; never wire live visuals/levels into it.
    - **A `customFace` block needs a thumbnail painter here too.** The tile
      builds its `Block` from the def and walks `faceItems`, which a custom face
      bypasses — so `cassette` and `roll` have explicit shells
      (`drawCassetteShell` / `drawRollShell`). A Piano Roll tile drew as an
      empty box for exactly this reason. Asset tiles go further and draw the
      asset: `renderCassetteThumbnail` puts the name on the label,
      `renderRollThumbnail` punches the roll's real notes into the paper.
  - **State** persists in localStorage: `livepatch.lib.pinned` / `.recent` /
    `.density`.
  - **Hover info card**: bigger thumbnail + description + colored port list,
    appended to `#float-layer` (inside `#app`, zoomed) and positioned via
    `toUiPx` — the UI-scale rule below. Verified correct at scale 1.0 and 1.45.
    - **It must be pruned whenever the grid rebuilds** (`pruneHoverCard`).
      `mouseleave` never fires on a *detached* element, so deleting a tile under
      the pointer — or any other re-render — stranded the card on screen until
      the pointer happened to cross another tile.
- **Properties** — the selection editor, generated from the block's `ParamSpec`s
  (range/enum/bool/string/**device dropdown** for hardware blocks, populated
  live from the native engine), plus per-CV-port cards (strength/bounds),
  per-port editing (edge/position/label/add/remove incl. `tape` kind), and style
  overrides.
- **Appearance** — the full theme editor (a schema over `Theme`), plus the UI
  scale (an app preference, not part of the scene's theme) and **Reset all to
  defaults** at the top, which resets both. Reset used to be right-click-only so
  it couldn't be hit by accident, which also meant nobody found it; the
  right-click still offers it, and a slider's own "type a value" menu now wins
  over the panel's (they used to fire together).
- **Scenes** — new/save/load/import/export + a saved-scene browser.

## Panel manager (`src/ui/dock.ts`) — lowercase "dock"

Panels dock into left/right/bottom zones or float; drag a header to detach, drop
near an edge to re-attach; zone splitters resize; everything persists to
localStorage. Zone sizes are clamped so docks can't squeeze the canvas out at
large UI scale.

`PanelDef.pinned` welds a panel to its `defaultZone`: no float button, no
tear-off drag, and a saved layout naming another zone is ignored. Only the Dock
uses it.

### A floating panel's size is UI px, and it must be clamped (2026-08-01)

"Detached windows extend all the way to the right, off screen, no matter what"
was one line: the per-panel `ResizeObserver` stored `getBoundingClientRect()`
straight into `float.w`. The rect is **viewport** px; `float.w` is written back
as a CSS px style value, which the UI zoom then magnifies. That is a positive
feedback loop with a gain of exactly `uiScale()` — `applyFloat` writes w → the
observer reads `w × scale` → stores it → the next `applyFloat` writes that. A
tear-off drag calls `applyFloat` once per pointer-move, so one drag at scale
1.45 is dozens of multiplications, and the runaway number is then **saved to
localStorage**, which is the "no matter what": every later launch came up
kilopixels wide. Same shape as the rig plan view's frozen-span bug below.

Two halves, both needed:

1. `toUiPx` on the observer's read — the actual bug.
2. **`applyFloat` clamps the size, not just the position.** Position-only
   clamping let a panel start at a legal `x` and still run past the right edge,
   and left no way back because the oversized width was what got saved. A panel
   may never be wider or taller than the window; a poisoned saved layout heals
   on the first paint. `sanitizeFloat` additionally rejects NaN/absurd values
   coming out of storage, because one NaN turns every later `Math.min` into NaN
   and the panel gets no size at all.

> **Naming, because it bites:** `dock.ts` is the *panel manager*. **The Dock**
> (capital D, `src/ui/dockpanel.ts`, panel id `dockpanel`) is one pinned panel
> registered with that manager. "Dock a panel" and "the Dock" are different
> things.

## The Dock (`src/ui/dockpanel.ts` + `clipview.ts` / `widgetdock.ts` / `advanced.ts`)

A bottom-pinned panel split into tabs by a **vertical rail** on its left edge
(deliberately not the Library's horizontal chips; it stays usable when the Dock
is short and scales past a handful of tabs). Resized by dragging its top edge —
that is the existing `#dock-bottom-splitter`, which is why the Dock is a normal
bottom-zone panel rather than its own window. Hidden by default; toggled from
the top bar.

Tabs are a **registry** (`registerDockTab`), so a new tab is a registration, not
an edit to the panel. Rail position comes from `DockTabDef.order`, *never* from
registration order — that is really module-import order, which the import graph
can reshuffle silently (it already did once: `editor.ts` imports `widgetdock`,
which put Widgets ahead of Clip).

Each tab's DOM is built **once** and shown/hidden. Rebuilding per switch would
throw away canvas state (clip zoom, in-flight peak scans) every time the user
glanced at another tab.

**One rAF loop.** Tabs get `onFrame(audioOn)` from `main.ts`'s single frame
loop and must never start their own (`docs/10-performance.md`). A closed Dock
costs one map lookup per frame. Document changes route as
`refreshDock()` (structure/selection — rebuilds DOM) vs `repaintDock()` (param
ticks — dirty flag only); a full refresh on every param would rebuild the clip
toolbar under the user's cursor mid-drag.

### Detaching the Dock to its own window (2026-08-01)

The Dock can move to a **second OS window** (`dock.html` → `src/dockwindow.ts`),
for a second display — typically a touchscreen. It is a *controller* for the
main window, not a second app, and it has **full parity**: all four tabs, the
deep editors, context menus, Arrange mode.

**The skeleton in `dock.html` is deliberately identical to `index.html`.** That
is what lets `dock.ts`, `menus.ts` and every modal run there unchanged — they
address those ids directly. `body.dock-window` is the only difference, and
`styles.css` uses it to drop `#workspace` so `#dock-bottom` fills the screen.

**`#canvas` still exists and still carries a real `Renderer` and `Editor`.**
They are hidden (0×0; `Renderer.resize` floors at 1×1), not stubbed — the Clip,
Advanced and Rig tabs call `drawVisualAt`, `runDockAction`, `startMidiLearn` and
`revealBlockAt`, and stubbing those would be a second copy of widget painting,
which invariant 10 forbids.

**The window never drives audio or CV.** `runtime.init()` and `runtime.start()`
are never called there. Both engine constructors are pure field initialisers —
`WebAudioEngine` builds its `AudioContext` in `start()`, `NativeEngineClient`
subscribes in `start()` — so the singleton sits inert and importing it is safe.
`src/ui/docklink.ts` then assigns a `RemoteEngine` over the **public, assignable
`runtime.engine`**, which is why the whole feature needs *no change to
`runtime.ts`* beyond one outbound `onParamSent` hook. That inertness is not a
nicety: this window is by construction the unfocused one, and rule 8 of
[`10-performance.md`](10-performance.md) is about exactly that.

Sync is **two-tier**, because the two kinds of change have opposite budgets:
`'param'` goes as coalesced deltas (both directions, one batch per frame), while
`'structure'`/`'meta'`/`'theme'` goes as a debounced full-scene snapshot. A
snapshot per param would ship the whole scene sixty times a second through a
knob drag; a patch format for structure would be work spent on the path that
already recompiles. A 1 s snapshot also runs as a *reconciliation backstop*,
because `doc.onChange` says a param moved but not which one. `applying` guards
every handler — without it the two windows trade one edit forever.

The dock window reports a **watch set** (`{nodes, params}`) built from the reads
themselves, so it always matches what is genuinely on screen. Both halves are
needed and they are not the same: visuals/steps/transports are per *node*, but a
CV/MIDI marker is per *parameter*. The engine only computes visuals for watched
nodes, so without this the detached window's scopes are simply dead.

#### Mirrored vs collapsed — measured, not guessed

When the Dock detaches, the main window **keeps a live mirrored copy by
default**. That is the opposite of the obvious call, and it is measured:
`LIVEPATCH_DOCKWIN_PERF=1`, 118 docked widgets over a 67-block patch, main
window per-frame *work*, three runs —

| configuration | mean frame work |
|---|---|
| attached (baseline) | 2.59 – 2.92 ms |
| detached + collapsed | 3.10 – 3.37 ms |
| detached + mirrored | 3.21 – 3.33 ms |

mirrored vs collapsed came out −4.3 %, +3.6 %, −1.2 % — noise.

**Why a second painting surface is free here:** collapsing gives the reclaimed
height to the *canvas*, and drawing a larger workspace costs more than drawing
the dock widgets it replaced. The real price of detaching is building and
sending the value frame, and that is paid in both configurations.

> **Measure the frame WORK, never the rAF interval.** The first attempt at this
> timed the gap between frames and reported that detaching cost +72 % and that
> mirroring *recovered* 36 % of it — confident, reproducible, and completely
> backwards. With two windows on one display the interval is set by compositor
> scheduling, which swamps the effect. `src/main.ts` exposes
> `__lp.frameStats` for this; it is off unless a harness turns it on.

#### The same Dock, over the LAN (`electron/lanserver.cjs`)

`dock.html` is an ordinary web page, so the *same* control surface can be
served to a phone or tablet. `src/ui/docktransport.ts` picks the pipe by
looking for the native bridge: present → Electron IPC (the detached window),
absent → WebSocket (a remote device). No message shape changes; the remote
control surface **is** the detached window, reached differently.

This is also why the phone case sidesteps everything that makes a full Android
port hard: the phone renders no audio, so all 25 native-only spatial kernels
stay on the desktop where they work.

**Security posture — this ships to other people's machines.**

- **Off by default and never persisted.** The server starts only from the
  dialog, and the "on" state is deliberately *not* remembered: off-by-default
  means nothing if a machine that tried it once comes back up listening.
- **Token-gated WebSocket**, compared with `timingSafeEqual`, freshly minted on
  every start so stopping the server invalidates every previously-issued link.
  The token lives in the URL *fragment*, which browsers never put in the
  request line — so it stays out of server logs and `Referer`. Static files are
  ungated by consequence (a fragment cannot authenticate a GET) and by choice:
  the bundle ships in the installer and is not a secret. What it cannot do
  without the token is *connect*.
  **The fragment protects against logging, not against sniffing.** The page
  puts the token in the WebSocket upgrade's query string and this is plain
  HTTP, so anyone positioned on the segment (open WiFi, a compromised device)
  can read it off the wire. That is the reason for "a network you trust", and
  it is stated in the dialog rather than implied.
- **Raw connections are capped** (`server.maxConnections`), separately from
  `MAX_CLIENTS`. The client set is only populated *after* the token check, so
  on its own it does nothing about an attacker who opens sockets and never
  authenticates — an unauthenticated fd exhaustion against the process that
  supervises the audio engine. Mutation-tested: without the cap the suite holds
  140 of 140 sockets open, with it 55.
- **Same-origin check on upgrade**, which is the anti-DNS-rebinding defense.
- **Every inbound message is validated** in `docklink.ts`, including from the
  local detached window. A token proves who connected, never what they send —
  and validating one pipe while trusting the other would make document safety
  depend on which socket a message arrived on. Non-finite param values are
  rejected at this boundary (golden rule 13).
- **Bounded everything**: frame size rejected from its *header* (waiting for
  the body is the attack), fragment reassembly, per-socket buffer, client
  count, handshake and idle timeouts, and **write backpressure** — a phone on
  bad WiFi drains slower than 30 value frames a second, and `socket.write`
  would buffer the difference in the main process forever. Dropping is correct
  there: a late meter frame has no value.

`scripts/lanserver-security-test.cjs` is the attack suite (30 cases, plain
node, no Electron). It was **mutation-tested**: disabling the origin check, the
frame-size check, the connection cap or the socket teardown each made it fail,
so those cases are load-bearing. Disabling the path-containment check did
*not* — see the comment at that check for why it stays anyway.

> **None of this is written as though it were secret, because it cannot be.**
> `asar: false` and `electron/**` in the packaged file list mean
> `lanserver.cjs` ships as readable plaintext in every installation — the
> source *is* the shipped artifact. Withholding detail here would cost the
> next maintainer real information and cost an attacker nothing. Anything in
> this section that would be dangerous to publish is a bug to fix, not a
> paragraph to delete; that is how the connection cap above was found.

> **A throw in the relay locked the app out of the user's hands.** An undefined
> symbol in the `dockwin:send` handler — which runs on every value frame — became
> Electron's main-process error dialog reappearing dozens of times a second,
> faster than it could be dismissed. `node --check` cannot catch an undefined
> reference. The handler now catches and logs to diagnostics: a bug in a hot
> relay must degrade into a dropped message, never a modal loop.

#### Traps found building it

- **`localStorage` is shared between the windows** — same origin. Four keys had
  to become per-window (`dock.ts` layout, `uiscale.ts`, `dockpanel.ts` active
  tab): with one key each, the detached window wipes the main window's
  Library/Properties arrangement the first time it runs.
- **`applyZoneSizes` writes an *inline* height**, so CSS cannot make the bottom
  zone fill. Hence `Dock.fill`, read from the body class rather than a setter —
  `makeZoneSplitters()` runs in the constructor of a module-level singleton, so
  any setter is necessarily too late to suppress the splitters.
- **Save `getNormalBounds()`, not `getBounds()`** (`electron/main.cjs`). The
  latter returns the screen rect while fullscreen, so closing from fullscreen
  saves the fullscreen size as the restore size and the window can never be
  small again — the same family as the floating-panel size bug above.
- **Validate saved bounds against the current displays.** This window lives on
  a second monitor, so "that monitor is not plugged in today" is the normal
  case, and restoring blind opens it where nobody can reach it.
- **`export let` reassigned as an install hook is a live-binding trap.**
  `runtime.onParamSent = sendParamToDock` copies the value at assignment, so it
  would capture the no-op placeholder and every param write would silently
  never arrive. The exports are real functions dispatching to internal state.

### Tab 1 — Clip (`clipview.ts`)

**A viewer with the selected block's own controls beside it — not an editor.**
Rebuilt 2026-07-23: the clip/arrangement system it used to be (split, join,
move, crossfade, consolidate, flatten) was removed wholesale. LivePatch is a
surround-sound sandbox and arranging audio is Ableton's job; see
[`README.md`](README.md). If you are about to add an edit here, that is the
decision to revisit.

Follows the selection: blank until a block in `TAPE_ROLES` (cassette, file
player, sampler, recorder, writer) or a roll block is selected. An *empty*
selection keeps the current target — clicking empty canvas mid-edit must not
throw the view away.

`TAPE_ROLES` is the only per-type branch in the file: it names which params
carry the bars/transport/loop/seek for each type, and flags the two special
cases (`recorder`, `sampler`). Adding a tape block to the tab is one entry
there. What each role gets:

| block | controls |
|---|---|
| cassette, tape-writer | nothing but the waveform + zoom |
| file-player | ▶ ■ ⟳, the play bars and their fades, scrub |
| sampler | mode (Classic / One-Shot / Slice), the region bars + fades, loop brackets and seam-fade (Classic), slice markers and the Divide/Detect/Clear tools (Slice) |
| tape-recorder | ● ▶ ■ Clear ⟳, the bars, scrub, **Save As…** |
| midi-roll / midi-recorder / midi-player | the piano roll, plus its own transport (below) |

**The play bars** are the loudest thing on the surface, on purpose: heavy stems
with grab heads at top and bottom, a scrim over everything they exclude, their
fade ramps hanging off them, and the window's length labelled between them.
They are hit-tested **first**, so nothing else can steal a grab from the
transport. `regionHandleAt` reaches their fade diamonds only once a fade
exists, so a plain click near a bar always gets the bar.

**The interaction model:**

- **A plain drag pans.** This is a viewer; a drag on empty surface must not
  select or create anything. Wheel zooms at the cursor, Shift-wheel and
  middle-drag pan, `F` fits, Space plays.
- **The window selection is opt-in, which is what keeps that rule true.** The
  ▭ tool makes a drag pick a time range instead of panning; Ctrl does it for a
  single gesture (in the sampler's Slice mode, Ctrl-click still drops a slice —
  that test runs first and returns). The cursor switches to a crosshair so the
  change of gesture is visible before the button goes down.
- **The playhead is grabbed directly** (on its bar or the ruler) to scrub, and
  only on blocks that have a `seek` param.
- **Hit order is bars → loop brackets → slice markers → pan**, and Ctrl-click
  in Slice mode is tested *before* all of them: it is a deliberate modifier and
  must not be stolen by a marker that happens to be nearby.
- **Marker snapping** uses a screen-pixel tolerance, so the magnet shrinks in
  musical terms as you zoom in and stops fighting precise work; Alt defeats it.
  Candidates are the file ends, the play bars, and the other slice points.
- **Loop drags are start+length, not start+end** — that is what Ableton's Loop
  and Length knobs mean and what both kernels read, so dragging the *start*
  keeps the length and dragging the *end* changes it.
- Slice markers are written **unsorted**; `parseSlicePoints` re-sorts and
  de-dupes, so dragging one past its neighbour reorders the kit rather than
  colliding.
- **A recorder mid-take** draws from `VisualFeed.wave` instead of scanning a
  cassette — there is no file yet. The moment ■ commits, `params.asset` fills
  in and the ordinary cassette path takes over. A MIDI recorder does the same
  through `VisualFeed.notes` into a read-only `RollData`.

#### The window selection (2026-07-25)

A scratch time range (`winSel`, 0..1 of the file) that says *where the next
action applies*. It is not a clip and not an edit — nothing persists it, and it
is dropped when the target changes. Re-added deliberately narrow: the
arrangement system that was deleted on 2026-07-23 is not coming back, but
"zoom/audition/trim **this bit**" is a viewer's job, not a DAW's.

What it feeds, all shown on the toolbar only while a range exists:

| action | who gets it | what it does |
|---|---|---|
| `⤢ Zoom` | anything | view = the selection |
| `▶` / Space | player + recorder | plays the selection instead of the bars |
| `Delete` / ⌦ | **recorder only** | cuts the range out of the take |
| `Save selection…` | **recorder only** | the range as a new cassette |

- **Auditioning parks the bars, it doesn't overwrite them.** The kernels read
  `regStart`/`regEnd`, so playing a range means putting the range *in* them and
  handing the originals back — on ■, when the selection changes or clears, when
  the target changes, and when playback ends on its own (`onFrame` latches
  `playing` first, so the gap between ▶ and the engine reporting it can't read
  as an end). There is no state where the user is left with bars they didn't
  set.
- **Delete/Save are recorder-only, and that is the rule from
  [`09-persistence-and-assets.md`](09-persistence-and-assets.md), not a
  limitation.** Assets are never rewritten destructively; the one exception is
  a recorder acting on *its own take*, the same exception that lets it punch
  in. A cassette in the Library is somebody's file.
- **A rewritten take keeps its id**, so every deck holding it follows the edit —
  which means the engine's decoded copy has to be evicted explicitly
  (`runtime.assetChanged` → `.pcm` rewrite → `asset-ready`), and the node is
  re-poked with the same asset id. Skip either and it keeps playing the samples
  it decoded before the cut. The edit is **not undoable**, like every other
  asset action, so it confirms first and says so.

**Waveform rendering — three rules that each fixed a real defect:**

1. **Scan only the visible slice.** Sizing the bucket request from the visible
   width but scanning the whole file renders a zoomed-in view at a fraction of
   the detail — the "blocky waveform" bug.
2. **Sample at device resolution** (`visibleCssPx * ratio`), not per CSS pixel.
   Per-CSS-pixel buckets are `ratio` physical pixels wide on a HiDPI or
   UI-zoomed display, which turns a waveform into a bar chart.
3. **Place each column by its own source position** (`getCassetteRangePeaks`
   returns the range it *actually* covers, which is quantized for caching).
   Assuming the scan covers what was asked for slides the waveform against the
   markers, subtly at low zoom and glaringly at high zoom.

The waveform is one filled envelope path (out along the maxima, back along the
minima) rather than a column of rects — no seams, and it anti-aliases.

**Sync vs async peaks.** `getCassettePeaks` is right for *drawing* (a repaint
cannot block; a change event brings it back when the scan lands) and wrong for a
*command*. "Detect transients" uses `getCassettePeaksAsync`, because a button
that gave up when its own bucket count was cold did nothing the first time it
was pressed.

#### The piano roll (`pianoroll.ts`) — 2026-07-25

The notes half of the Clip tab. Three rules it now enforces, each from a real
complaint:

- **A click and a stretch must be distinguishable before you commit.** They used
  to differ only by five invisible pixels at a note's right edge, so which one
  you got was a coin toss. `updateHover` classifies every pointer position
  (`note` / `stretch` / `bar` / `seek`), `cursor()` reports it to the host
  canvas, and the hovered note draws an outline — or a bright grip on its right
  edge — before the button goes down. A live length read-out follows a stretch.
- **No note may be shorter than one grid division** (`minLen()`, or `FREE_MIN`
  with the grid off). The resize floor used to be `q.t + 0.01`, so dragging an
  edge back past a note's own start left a sliver that was invisible at any
  zoom, impossible to click, and findable only by rubber-banding an apparently
  empty area. Both the draw and the length drags clamp; `removeTinyNotes`
  cleans up rolls that already contain them (offered on the context menu, with
  a count, only when there are some).
- **The transport is the same vocabulary as the waveform side.** Start/end play
  bars with grab heads, a scrim over what they exclude, the window's length in
  beats, and a draggable playhead with a head in the ruler. **Bars are
  hit-tested first**, then the playhead, then notes — nothing may steal a grab
  from the transport.

The roll knows nothing about blocks or params: the Clip tab resolves the player
and hands over a `RollTransport` (region fractions, playhead, and the writers
for both), exactly as it does for the waveform. **No player wired = no
transport = no bars**, which is honest — there would be nothing for them to
control. Mid-drag the pointer owns the playhead, so an engine frame can't yank
it back to where playback actually is.

The region is `regStart`/`regEnd` on the **Pianola** (`midi-player`), 0..1 of
the roll, honored by both engines: ▶ starts at `regStart`, a loop returns
there, playback ends at `regEnd`. Fractions rather than beats, so editing the
notes doesn't move the bars.

### Tab 2 — Widgets (`widgetdock.ts`)

Mirrored clones of any face widget in the patch (right-click a widget → "Add to
Dock", or "Dock all controls on this block"). **The clone drives the same param
on the same block** — it is the same widget drawn twice, so CV/MIDI indicators
and values track each other.

**Appearance is deliberately NOT shared.** Geometry and `control` (variant,
label, color, readouts, opacity) live on the `DockWidget`; `block.controls` is
untouched, and vice versa. Restyling a clone leaves the block face alone.

- Two modes: operate (default) and **Arrange** (`A` / the toolbar button) for
  move/resize/multi-select/restyle — mirroring the canvas's patch vs block-edit
  split, so no modifier key has to fight widget dragging.
- Snapping: 8 px grid first, sibling edge/center alignment wins, guides drawn
  only for snaps that actually applied (same rule as face editing).
- Right-click: Control/Style/Appearance submenus (the menu API has no real
  submenus — a "▸" item reopens `showContextMenu` at the same anchor), CV port
  add/remove, MIDI learn, "Source: …" (reveals the block via
  `Editor.revealBlockAt`), Remove.
- **CV ports appear on the source block**, in the workspace — that is the only
  place a wire can physically reach. MIDI learn writes to the source block's
  `midiMaps`, so a clone and its origin share one binding (they are one param).

> **The canvas may only outgrow the pane when there is content to scroll to**
> (fixed 2026-08-13). `resizeCanvas` runs once per frame and wrote the canvas's
> CSS size from `Math.max(80, scroller.clientWidth)` / `Math.max(60, …Height)`.
> On a slim dock that floor is larger than the pane, so the canvas overflowed,
> `overflow: auto` put a scrollbar up, the scrollbar took its width back off
> `clientWidth`, and the next frame sized the canvas from the smaller number and
> took it away again — a loop with nowhere to settle. The empty-state hint is
> centred on `vw / 2`, which is exactly the number oscillating, so it read as
> **the text shaking**. Sizing from `needW`/`needH` when there IS content is
> stable for the same reason: the scrollbar changes `avail*`, which no longer
> feeds back into what the canvas asks for.
>
> Any per-frame `canvas.style.width = f(clientWidth)` inside an `overflow: auto`
> box is this bug waiting to happen. `f` must not be able to exceed its input
> unless something other than the input decides the result.

#### Docked visuals are interactive too (2026-08-02)

`beginOperate` opened with `if (!spec0) return false`, and a `'visual'` ref
never has a `ParamSpec` — so **every** docked visual was inert. It was reported
as "the matrix widget in the dock doesn't do anything", but the EQ curve and the
Speaker Monitor's bars were equally dead, all three from that one guard. A
surface that paints a live matrix and ignores every press reads as broken, and
on a detached touchscreen — the whole point of the Dock — there is no canvas to
fall back to.

`beginOperateVisual` handles them, reusing the exported geometry the canvas uses
so a cell is in the same place on both surfaces: `matrix` (click toggles a
crosspoint, shift toggles half-open), `eq` (drag a band handle; shift = Q), and
`speakers` on a `speaker-monitor` (click mutes, shift-click solos).

Two traps, both of which look fine in a flat test patch:

- **Write through `facepaint.ts` with `r.nodeId`, never `runtime.nodeId(b.id)`.**
  The canvas's node id is relative to the open subgraph; the Dock resolves
  widgets from *anywhere* in the scene. A local `runtime.sendParam` addresses
  the wrong node the moment the source block is not in the open graph — and the
  detached window and the LAN surface both reconstruct the target by absolute
  path (`docklink.ts`). `writeParamId` exists because `writeParam` needs a
  `ParamSpec` a visual ref does not have.
- **The parse/mutate/serialize round trip belongs in `core/matrix.ts`**
  (`setCrosspoint`, `toggledCrosspoint`). It was hand-written at three call
  sites; three copies of an index calculation is how two surfaces end up
  disagreeing about which cell you clicked.

Known gap, stated rather than left to be discovered: the Dock passes
`overlay: undefined` to `drawVisualAt`, so a dragged EQ band does not highlight
the way it does on canvas. The drag works; only the hot-band tell is missing.

**Any widget can be docked on its own.** The Add/Remove-from-Dock menu item used
to live inside `widgetItems()`, which is only spliced in when a *param* widget
resolves — so a Matrix, EQ, scope, meter or speaker display could only reach the
Dock via "Dock all controls on this block", which drags along every knob you did
not want. It is now keyed on the face item (`dockItems` in `editor.ts`).

### Tab 3 — Advanced (`advanced.ts`) — foundation only

**No editor is implemented yet, on purpose.** What exists is the seam:
`registerAdvancedView({ id, title, match, build })`, target resolution
(`advancedCandidates()` already lists the selection's eligible widgets), and the
build-once/show-hide/onFrame lifecycle shared with the other tabs. The
placeholder names the eligible widgets so the tab reads as scaffolding rather
than as broken. Adding the EQ or sequencer editor should touch only a new file

### Tab 4 — Rig (`rigview.ts`)

The scene's speaker layout, on one canvas split into two linked panes sharing a
selection:

- **PLAN** (left) — from above, front up. Drag = azimuth + distance.
- **DIRECTION** (right) — azimuth × elevation. Drag = where the speaker points.

**The right pane is a chart, not a side view, and that is load-bearing.** A
true side elevation projects front and back onto the same place: in a 7.1.4
rig, `Ltf` (az 45, el 45) and `Ltr` (az 135, el 45) land on the *identical
pixel*, so half the height speakers become unclickable and you silently edit
the wrong one. This was built as a side view first and the bug was caught by
clicking Ltf and watching Ltr get selected. Charting azimuth against elevation
separates distinct directions by construction.

- Each pane owns **distinct fields** (plan: azimuth + distance; direction:
  azimuth + elevation), so dragging in one never silently undoes the other.
- The number drawn inside each speaker is its **bus channel** (index + 1).
  Speaker order *is* channel order, which makes this tab the legend for what
  every channel of a wide wire means — the same names the wire's hover legend
  shows.
- Subs (`lfe`) draw as squares, not circles: they are not pannable, and should
  not look like something you can steer a source onto.
- Toolbar presets (Stereo → 9.1.6) replace the layout wholesale. That
  renumbers every channel, so it is a real edit with a real undo step. The
  picker also lists the user's **saved rigs** and the two actions that manage
  them (＋ Save current rig… / ✕ Delete a saved rig…) — see
  [`09-persistence-and-assets.md`](09-persistence-and-assets.md). Both save and
  load deep-copy, so later speaker drags never edit the stored preset.
- **History:** the drag pushes history on the *first move*, not on
  pointer-down, so clicking around to inspect speakers doesn't bury the undo
  stack under no-ops. Intermediate moves are `live` (no push), so one drag is
  one undo step.
- Rig edits arrive on the **cheap repaint path** (`repaintDock`), not
  `refreshDock` — a speaker drag fires one change per pointer-move, and a full
  refresh would rebuild every other tab's toolbar mid-drag.

#### The plan view's scale must be frozen while dragging (2026-07-24)

The plan view turns a pixel radius back into metres by dividing by `k`, and `k`
came from an auto-fit scale derived from the furthest speaker. That is a
**positive feedback loop**: drag outward → distance grows → the view zooms out
→ the *same cursor position* now reads as a larger distance → repeat, with the
cursor perfectly still.

The gain is exact and brutal: with the cursor at 92 % of the radius and the
auto-fit headroom at 1.25×, each pointer-move multiplies the distance by
`0.92 × 1.25 = 1.15`. Forty moves is ~270×, and a real drag emits far more —
which is why a speaker walked off to thousands of metres.

`frozenSpan` pins the scale for the whole gesture, which **removes** the loop
rather than damping it. `DIST_MAX` (100 m) is belt-and-braces, not the fix.
On release the drag's scale is kept (`userSpan`) instead of snapping back to
auto-fit, since a view that jumps on pointer-up makes it impossible to judge
what you just did.

- **Zoom**: wheel over the plan pane; `Fit` returns to auto-fit and lights up
  while auto. The **direction pane deliberately does not zoom** — its fixed
  ±180°/±90° framing is exactly why a speaker's position in it means the same
  thing from one rig to the next.
- Speakers can legitimately **overlap in plan** (in 7.1, `C` at dist 2 and
  `LFE` at dist 2 elevation −10 project 0.03 m apart). That is not a bug — it
  is what the direction pane is for. Don't "fix" it by nudging positions.

#### Calibrate (`rigcal.ts`, 2026-07-31)

Measure each speaker with a microphone and correct its frequency response,
level and arrival time. The dialog lives here because the thing you measure is
the thing drawn two inches below the button. The maths is in
`src/core/calibrate.ts`, the sweep playback in
[`06-audio-io-and-latency.md`](06-audio-io-and-latency.md), and the filter that
comes out in [`05-native-engine.md`](05-native-engine.md).

The flow: pick the microphone input (any WASAPI capture device or ASIO driver,
or the ASIO master's own input) and its channel; optionally load a microphone
calibration file (UMIK-1 / REW `freq dB` text — "no file" means a flat mic);
Measure. Each speaker plays a 1.2 s sweep; results are written back as **one
undo step**.

- **The output route is not a picker.** It comes from the patch's `speaker-rig`
  block (driver + device). A calibration is only valid for the signal path it
  was measured through, so offering a second route here would let the user
  measure a chain nobody hears — and would be a second place to set the driver
  that can disagree with the first. No Speaker Rig in the patch → the dialog
  says to add one, rather than starting a run that can only fail.
- **It moves speakers.** Measured arrival times give the *spacing* between
  speakers exactly and the absolute distance not at all (the driver stack's
  round-trip latency is unknown and common to all of them), so the measured
  spacing is anchored to the mean of the distances already in the rig: relative
  geometry from the measurement, overall scale left where the user put it. The
  summary says so and Ctrl+Z puts everything back.
- **Green = calibrated**, and it is the **fill**, while hover is a **ring**.
  Both were the fill originally, which would have made a hovered speaker
  indistinguishable from a calibrated one — and "which of these have I
  measured" is a question you ask while the pointer is on the canvas, i.e.
  exactly when the two collide. A calibrated **sub** keeps its square (that
  shape means "not pannable" and is load-bearing) and gets a green halo instead.
- The toolbar button reads `◉ Calibrated 5/8` and lights accent-coloured, so
  the state is legible without hunting for a green dot in a dense rig. The hint
  line dates the selected speaker's calibration and names the mic file.
- Right-click a speaker for *Calibrate this one* / *Clear this calibration*.
  Per-speaker actions belong on the dot; the toolbar has no way to say which
  speaker it means.

**A calibration expires when the speaker stops matching it.** `calStale`
(`core/rig.ts`) compares the live speaker against the `at` baseline stored with
the measurement, and `GraphDoc.setRig` drops any that no longer match — so a
speaker turns blue the moment you drag it past tolerance. Two details are
load-bearing:

- **The tolerance is not zero** (0.5° / 2 cm). A calibration is minutes of
  sweeps and a click that lands one pixel off moves a speaker by a hundredth of
  a degree; discarding it for that would make the feature unusable in the very
  editor it lives in. Renaming keeps it — a name is not a measurement.
- **It keys on the *effective* hardware channel, not the `out` param.** A
  speaker with no explicit `out` sits on index + 1, so deleting an earlier
  speaker silently re-points this one at a different amplifier channel, and the
  old measurement is then a measurement of something else. That is why
  `calStale` takes an index.

The check lives in `setRig` rather than in each caller because *every* route
into the rig — drag, inspector, preset, ± Speaker, undo, scene load — goes
through it, and the delete-renumbers case is exactly the one a per-caller check
would miss. `dropStaleCals` returns the same object when nothing is stale, so a
drag pays one comparison per speaker per pointer-move and allocates nothing.

## Shared face-widget painting (`src/ui/facepaint.ts`)

A face ref (`param:` / `link:` / `expose:` / `visual`) is now drawn in two
places: on a block face, and as a Dock clone. Both go through
`paintFaceWidget`, and both get their live post-CV markers and binding badges
from `modOf` / `modSrcOf` / `drawBindingBadges` here. This is invariant 2
(renderer and editor share widget geometry) extended to a third consumer —
the Dock must not grow a second copy of the widget math.

- `resolveRefAtPath(path, ref)` resolves a ref against a block addressed by its
  **absolute path from the scene root**, for the Dock (whose widgets live
  anywhere, regardless of which subgraph is open). `Renderer.resolveOnFace` is
  the hot-path equivalent for the open graph — a direct lookup, no path walk,
  because it runs per widget per block per frame.
- `WIDGET_DRAG_PX` / `dragNorm` are shared so a knob turns at the same speed on
  both surfaces.
- Live visuals stay on the Renderer (`drawVisualAt`) because they own per-node
  offscreen caches; the `surface` argument keys those caches so a mirrored
  spectrogram scrolls on its own clock instead of stealing the canvas's frames.

## UI scale (`src/ui/uiscale.ts`) — a recurring trap

The whole chrome zooms via **CSS `zoom` on `#app`** (`--ui-scale`). Zoom scales
layout, text, and hit areas together (a transform would not). **The canvas is
deliberately left at 1:1** — patches have their own view zoom.

Range is `UI_SCALE_MIN` 0.6 … `UI_SCALE_MAX` **4** (raised from 2.5 on
2026-07-25). The old ceiling was a real limit in daily use rather than a safety
margin: on a 4K panel the useful range starts around 200 %, which left the
slider pinned at its top with nothing above it. Nothing breaks up there because
everything that could — fixed-size canvases, menu and panel placement — already
goes through `toUiPx` / `fitCanvasBacking`.

**Consequence you must respect:** inside `#app`, CSS pixels are "UI px" =
viewport px / scale. `getBoundingClientRect()` and pointer coordinates stay in
*viewport* px. So any code turning a pointer coordinate into a style value, or
hit-testing a fixed-size canvas, must convert:

- Chrome geometry (dock drag, splitters, floating panels, menus) uses `toUiPx`.
- The **main workspace canvas is safe** because it derives its size from
  `getBoundingClientRect` — the zoom cancels.
- A **fixed-size canvas is not safe.** The shape editor (`shapeeditor.ts`,
  420×320 set via `style.width`) once had dead vertex dragging, dead add/delete,
  and freehand drawing offset from the cursor at any scale ≠ 1, because it
  hit-tested pointer coords against unscaled logical coords. Fixed by mapping
  the pointer through the measured rect:
  `((clientX - rect.left) / rect.width) * CW`.

**Symptom signature for this class of bug:** everything pointer-driven in *one*
widget is dead or offset, and it works fine only at scale 1.

## Menus & modals (`src/ui/menus.ts`)

`window.prompt`/`alert` are unavailable in the Electron renderer. Use
`showContextMenu`, `promptModal`, `confirmModal`, `buildModal` — all in
`#menu-layer`/`#modal-layer`. Modal input keydown must `stopPropagation()` so
global editor shortcuts don't fire while typing.

### A menu label is DATA, not markup (2026-08-05)

**Build every label with `textContent`. Never interpolate one into
`innerHTML`.** `showContextMenu` did the latter for a long time, and it was a
real XSS: labels are not all literals — they interpolate block names
(`widgetdock.ts`), speaker names (`rigview.ts`) and custom-block titles
(`panels.ts`) — and **a block name travels inside a shared `.lps` scene**. So
importing someone's scene, then right-clicking the block, was enough to execute
its name. Nothing about the sandbox saves you here either: page script reaches
the preload bridge, and that bridge offers `keysSend` (synthesize any keystroke
into Windows), `lanStart` and `updatesInstall`.

Two things make this cheap to keep right:

- **No label needs HTML.** The `●`/`▸`/`○`/`✓` markers are plain text, and a
  sweep of `src/` found no label carrying a tag or an entity. If you ever want
  emphasis in a menu item, add a class and style it, don't ship markup.
- `innerHTML = ''` to *clear* a layer is fine, and so is a static template with
  no `${}` in it. The rule is specifically about interpolating a runtime string.

Same reasoning applies to anything else that renders a user-supplied name —
scene names, cassette names, VST plugin names (those come out of third-party
binaries). Found by CodeQL `js/xss-through-dom`; see
[`11-packaging.md`](11-packaging.md) for how that scan is wired up.

## Loop wires (`Renderer.loopNets`, 2026-07-28)

Cycles in a patch are **legal**: the executor's topological sort appends what it
could not order, so a node in a ring reads the previous quantum's buffer
(`engine/src/graph.ts`) — one quantum of delay, which is exactly what the
Feedback block is built around.

The problem was never correctness, it was legibility. A ring's wires look like
every other wire, so an accidental loop reads as a *broken block* ("why is this
screaming?") rather than as the topology you actually built. Wires on a cycle
now draw with `theme.wireLoopColor` as their **border**, leaving the signal
colour to carry level as usual.

- Membership is Tarjan SCC over blocks, run inside `netStyles()` and therefore
  cached against `doc.netRevision` — once per rewire, never per frame.
- The DFS is **iterative**. A recursive one is shorter, but patch depth is user
  data and blowing the JS stack while *drawing* is not an acceptable failure.
- A net is on a cycle when one of its sources and one of its sinks share a
  non-trivial component (or a block feeds itself). This is per-*net*, not
  per-block, which matters: a straight wire into a block that also sits in a
  ring is correctly left untinted.

## The Comment block (`Renderer.drawCommentFace`, 2026-07-28)

`customFace: 'comment'`, `noCompile: true` — canvas-only scenery that never
reaches an engine (see [`02-core-ir.md`](02-core-ir.md)). It draws no title:
face items are empty for any `customFace`, and a Comment *is* its text.

- Text **word-wraps to the block**, so resizing reflows rather than clipping the
  right-hand edge. Wrapping is measured per word each frame; comments are few
  and short, and a cache keyed on `(text, size, w)` would need invalidating on
  four inputs. If it ever shows up in a frame profile, measure before caching.
- Overflow **clips**; it does not shrink the font. Silently rescaling type is
  how two comments end up at sizes you never chose.
- Double-click edits the text (`promptTextModal`, multi-line, Ctrl+Enter to
  accept) instead of renaming the block — the name is never drawn.
- `ParamSpec.multiline` gives the param a textarea in Properties.

### An artwork face clips to the block's real outline, and its field stays inside it (2026-08-13)

Two rules, both learned on Mycelium, both applying to every `customFace`:

**1. One clip, round `traceBlockShape`, over everything the file draws.**
`entangleface.ts` already did this and said why: these plates are made of
rectangles and bands, and without the clip they square off the block's chamfers
and sit *over* the outline instead of inside it. `myceliumface.ts` clipped its
plate to a plain rounded rect while the block is a chamfer, and left its rivets,
its caption and its tap indicator lines unclipped entirely. One clip covers the
module and nothing added later has to remember the shape.

**2. A geometry helper's minimum must not be able to escape the block.**
`myceliumField` floored the field's **size** at 24 px while pinning its
**origin** at a fixed inset, so a block dragged smaller than the chrome around
it grew its loam, hyphae and fruiting bodies straight out of the bottom-right —
measured at 51 px of overhang on a 160×120 block, and reported as *"the mycelium
stuff grows outside of the widget's bounding box"*.

> **`def.minW`/`minH` do NOT bound a hand resize.** `Editor.applyResize` clamps
> at 44×30, and a `customFace` block is exempt by definition from the "too tight
> for its widgets" floor that stops ordinary blocks shrinking. So any size down
> to 44×30 is reachable and every face-geometry helper has to survive it. The
> chrome gives way first: the insets are what the field would *like*, not what
> it gets, and when even the minimum will not fit the origin is pulled back in.

## The Entanglement Field (`entangleface.ts` + `core/entangle.ts`, 2026-08-06)

A router with no DSP of its own: wire ends are dropped **anywhere inside its
viewport**, latch where they land, and it secretly permutes which input leaves
by which output. Everything a signal passes through between entering and leaving
is the user's own patch, re-ordered behind their back.

Four things here are worth knowing before touching it.

### `customFace` means "as well as", not "instead of" — for this one block

Every other `customFace` (`cassette`, `roll`, `comment`) replaces the face
entirely: `drawBlock` sets `items = []` for them. The Entanglement Field is the
exception and the exception is deliberate — **its plate is artwork, but its
controls are real params**. Advance, Reverse, Settle and Level are ordinary
`ParamSpec`s with ordinary widgets, painted by `facepaint.ts` on top of the
artwork, because that is the only way they mirror into the Dock, take a MIDI
learn, accept a CV port, and export onto the face of a custom block built
around this one. Hand-drawn arrows would have had none of that, and would also
have been a second copy of hit geometry for the face and the Dock to drift apart
on (invariant 2). The one-line carve-out is in `drawBlock`.

The consequence is that the artwork's geometry has to **clear the face layout**,
and it has to do it by *asking* rather than by a constant. `fieldTop()` in
`entangleface.ts` takes the real `faceItems(b)` and starts the glass under the
lowest of them. A fixed number was right for exactly one case: the block ships
with an authored one-row layout (`entangleLayout`), but a block saved before
that layout existed has none and falls back to `autoFace`'s two rows, and the
user can drag a widget anywhere afterwards or expose a CV knob. The constant was
right for the first and put the knobs inside the glass for the rest.

Three bands stack above the glass, and the numbers are shared between the
artwork and `entangleLayout`, so a change to one is a change to both:

| band | block-relative y | what sits in it |
| --- | --- | --- |
| flange | `0 … FLANGE_TOP` (22) | bolts, corner screws, closed by a scribe line |
| plate | `22 … 44` | the **title**, its ink centred: `padTop` 20 |
| recess | `44 … glassTop − 8` | the control row |

Two ways to get this wrong, both of which we have already shipped once:

- **The title is drawn on the middle line of its box** (`render.ts`, baseline
  `middle` at `y + TITLE_H / 2`), so `padTop` positions the *text* at
  `padTop + 9`. At 30 that put the text across the top edge of the recess; at 22
  its ascenders touched the scribe line above. Centring the *box* in the band
  (23) is still not centring what you see: the box's middle line splits the em
  square, and the ink is not symmetrical about it — measured off the canvas, the
  glyphs run from the cap tops down to the `g` descender, which at 23 left 8 px
  of air above and 1 px below. `padTop` is **20**, which puts 4 px on each side
  of the ink. If you change the title font size, re-measure it the same way
  rather than recomputing the box.
- **A widget that prints a panel mark is `MARK_H` (13 px) taller than
  `widgetSize` says** (`layout.ts`, `withMark`). Settle carries `mark: 'decay'`,
  so its stored height is 73, not 60 — a stored 60 hung the glyph out of the
  recess and over the scribe line below. The recess is drawn from a fixed top
  down to 8 px above the glass, so `CONTROL_AIR` is the only thing setting the
  air *under* the row: it is 16 (= 8 px of clearance + that 8 px overlap) so the
  row has 8 px above it and 8 below.

If you add a param to the block, re-check both.

For the same reason the block is created with **`autoSize: false`**
(`GraphDoc.makeBlock`). An auto-size block grows to wrap its *face items*, and
the viewport is not one — so an auto-size field would shrink to the height of
its control rows and clip the only part anyone is looking at.

### The routing is planned in the document, not in a kernel

`core/entangle.ts` traces the surrounding graph to find which outputs come back
round to which inputs, and which reach a real destination, then picks a
permutation that lets a signal which enters actually leave. A kernel is handed
its own port buffers and nothing else, so it could not make that promise. The
result ships as a `route` param string exactly the way the Matrix ships `grid`,
and `CompiledGraph` stays the only editor↔engine contract.

Two rules inside the planner, both of which were wrong at first:

- **A dead end is not a destination.** A block with audio outputs that nothing is
  plugged into is somewhere a chain *stops*, not somewhere it may legitimately
  end. Counting it satisfied the "a signal that enters can leave" promise by
  routing everything into an unwired reverb — technically a terminus, audibly
  silence. Only a block with no audio outputs at all (an output device, a rig, a
  recorder) is a destination.
- **`routeAt(seed, index)` is a pure function.** That is what makes Reverse an
  exact retrace instead of "another random patch". Do not give it state.

Small terminal counts enumerate the whole configuration space, filter it to the
valid ones and shuffle once, so the walk visits every configuration before
repeating — and only then wraps, which is the "it never loops unless the number
of terminals physically requires it" behaviour. Large counts hash-sample with
rejection.

### Terminals are ports, created on the drop

`style.freePorts` + `Port.free` (block-box fractions) already does everything
needed: the socket rides the block when it moves and holds its place in the
field when it is resized. `Editor.fieldLatchAt` decides the direction from the
*other* end of the wire — a cable from an effect's output makes an input, a
cable to an effect's input makes an output — and returns null when the far end
says nothing, rather than guessing.

A terminal with no wire is a ghost, not a spare: `syncEntangleTerminals` (inside
`syncRigPorts`, with the Matrix and the packers) removes it and re-plans. Ids are
a high-water mark and never recycled, so a wire can never inherit a dead
terminal's identity by landing on its id.

### The picture describes the routing without disclosing it

The tracks join terminals that really are connected — nothing here is invented
telemetry — but they are drawn as *residue*: each surfaces and fades on its own
slow cycle, never all at once, with drifting curl fragments that join nothing
among them. One track per field persists, because a glass with nothing on it
reads as broken rather than as secretive. You can learn that something is
happening between two sockets; you cannot read the patch off it.

`paintEntangleFace` **returns whether it wants another frame** and `drawBlock`
turns that into `dirty`. It does not live in `src/ui/visuals/` and must not: that
folder is a deletable additive layer, and without this module the block has no
face at all.

### It takes every cable kind, and only ever pairs like with like

A terminal takes the kind of the cable dropped on it — audio, MIDI, tape or roll
— and `routeAt` plans **one permutation per kind**, all sharing the seed and the
walk index so a single press of Advance moves all of them. There is no sense in
which a note stream could leave by an audio jack, and the compiler would reject
the net anyway.

Making that work needed a real addition to both engines, because the event
interfaces had no port dimension at all: `midiIn(ev, offset)` said nothing about
which cable an event arrived on, and `midiOut` was one callback per kernel, so a
kernel with three MIDI outputs could only ever broadcast to all of them.
Per-port events are now:

- `Kernel.midiIn(ev, offset, port)` / `Unit.midiIn(ev, port)` — the executor
  already knew the sink port, it was simply dropping it.
- `Kernel.midiOutAt(port, ev, offset)` / `Unit.setMidiOutAt(port, cb)`, built
  only for kernels that declare **`multiPortEvents`**. Opt-in because every
  other event block has exactly one in and one out, and a map lookup per event
  for all of them would be cost for nothing.
- The same pair for tape/roll (`tapeIn(id, port)`, `tapeOutAt`).

`scripts/entangle-routing-test.cjs` guards both halves: that an ordinary
single-port MIDI chain still delivers (that shared path is used by every MIDI
block in the app, and a regression there is silent — notes just stop arriving),
and that the field permutes per terminal without broadcasting.

Events get **no crossfade**. `settle` is a gain ramp and there is no such thing
as half a note-on, so a re-route takes effect on the next event.

### Not yet: CV- or MIDI-driven Advance

Advance/Reverse are `ParamSpec.docAction` — executed by `Editor.runAction`
wherever they are pressed (face, Dock clone, custom-block face). They are
deliberately **not** CV- or MIDI-drivable: both of those arrive inside an engine,
which cannot see the graph the route is planned from. Wiring a clock to the
field wants the engine→renderer transport pattern in
[`08-extending.md`](08-extending.md) — a kernel-side edge counter published
through `visuals`, which the renderer turns into a re-plan. Until that exists the
capability is absent rather than fake, because a CV port that looked like it
advanced the field and silently did nothing is the exact trap docs/08 warns
about. `settle` and `gain` are ordinary values and take CV normally.

## The Trajectory deep editor (`advpath.ts`, 2026-07-29)

The second Advanced-tab editor after the EQ curve, and the pattern to copy for
the next one. It matches `r.visual === 'path'`, draws a top-down plan of the
`path` block's waypoints, and lets you place/drag/delete them, set per-waypoint
height with the wheel (mirroring the EQ editor's wheel-for-Q), and capture a
freehand gesture with Record.

- The curve is drawn with the **same `samplePath`** the face preview uses and
  the kernel mirrors (`core/trajectory.ts`) — one source of truth for the
  shape, three consumers (editor, face, kernel).
- Every edit writes the `points` param through `block.params` +
  `runtime.sendParam` + `doc.touch('param')`, exactly like the EQ editor, so
  both engines and the face summary stay in lockstep. Changing waypoints is a
  `'param'` change, **not** `'structure'` — the kernel reparses in `setParam`,
  no recompile (docs/08 rule 8).
- The live playhead reads `runtime.modValueFor(nodeId, 'x'/'y')`, fed by the
  kernel's `liveParams`. Present on native, `null` on the web preview — the
  playhead simply doesn't animate there, the right degradation for a
  native-only spatial block.

### The two things that made it unusable (fixed 2026-07-30)

Both were about *editing* a path rather than about the path math, and both made
the block look like it only worked for the shape it shipped with.

- **A new waypoint used to be appended.** On a closed path that always drops it
  on the last→first leg, however far from the click that leg runs — so a
  four-corner path grew "between 4 and 1" wherever you clicked and could only
  be extended at one place. `insertIndexFor` (`core/trajectory.ts`) measures the
  click against the **drawn curve**, segment by segment, and returns the leg to
  splice into; an open path still appends/prepends past its free ends, which is
  where an open path is meant to grow. The new point's height is interpolated
  from its neighbours, so inserting into a lifted stretch doesn't drop it to the
  floor. The context menu also has explicit Insert before/after for when the
  legs are too close together to aim at.
- **Record ran out of points mid-gesture.** Capture wrote waypoints straight
  into `points` and stopped at `MAX_PATH_POINTS`, which a hand-drawn gesture hit
  in about two seconds: you could not finish a figure-eight, and what you got
  was the *first two seconds* of your drawing. Capture now keeps the raw stroke
  separately and **simplifies** it into the path (`simplifyPath`, RDP with the
  tolerance bisected to fit), so the whole gesture always survives at whatever
  fidelity the budget buys — the ceiling costs detail instead of costing the end
  of the drawing. The raw stroke has a ceiling of its own that widens the capture
  spacing and re-thins in place, so a gesture can run indefinitely without
  unbounded memory. The ceiling itself went 64 → 256; **it is mirrored in
  `engine/src/dsp.ts`**, which preallocates its point arrays at that size.

Past 40 waypoints the handles shrink to dots and lose their numbers — a recorded
path has too many for numbered discs to read as anything but noise — and the
curve is sampled at ≥ 8 steps per segment so a dense path doesn't draw as its own
chords.

## The Matrix deep editor (`advmatrix.ts`, 2026-07-30)

The third Advanced-tab editor. It matches `r.visual === 'matrix'` and is a grid:
inputs across, outputs down, one cell per crossing.

- Cell geometry is **shared with the block face** (`matrixFaceRect` /
  `matrixGeom` / `matrixCellRect` / `matrixCellAt` in `widgets.ts`, painted by
  `render.ts drawMatrixFace`) — invariant 2. **The face is no longer read-only**
  (2026-08-01): a click on it opens or closes that crossing and Shift-click sets
  it half open, handled in `editor.ts widgetDown` next to the EQ handles and the
  speaker meters. A router you can only rewire from the Advanced tab is a router
  nobody rewires. That is what now *forces* the sharing — `matrixFaceRect` exists
  precisely so the face's `r.x + 3` inset is not hand-copied into the hit-test,
  where being three pixels out is a click that lands one cell over.
- Click toggles a crossing, drag across cells paints a run of them to whatever
  the first cell flipped to, Shift-drag / wheel / two-finger drag set the
  crossing's gain, right-click gives the row and column operations. The
  unmodified gesture is the toggle because the grid is mostly used as on/off.
- **The `%` field states a level rather than approaching one.** Dragging and the
  wheel are for *finding* a gain; "−6 dB on this crossing and nothing else" is a
  number, and a router is exactly where you want to type it. It edits the
  **selected** cell (amber outline), not the hovered one — hover cannot do that
  job, because the moment the pointer leaves the grid to reach the field the
  hover is gone and the field points at nothing. Touching any cell selects it;
  the dB equivalent is shown beside the box, since that is the unit a crossing
  is actually judged in.
- **The port counts are edited here and they are topology.** `Ins`/`Outs` go
  through `doc.syncRigPorts()` and raise `'structure'`, mirroring what
  `Editor.setParamLive` does for the same params; everything else on this
  surface is an ordinary `'param'` write.

## Invariants (UI-specific)

1. **Fixed-size canvases inside `#app` must normalize pointer coords through
   their measured rect.** (UI-scale trap.)
2. **Renderer and editor must share widget hit geometry** — put it in
   `widgets.ts` and import it in both, never duplicate the math.
3. **Add a `widgetSize` entry** whenever you add a `WidgetKind`.
4. Panels rebuild their DOM on refresh; guard against clobbering an in-progress
   edit (`editingInside`).
5. **The workspace canvas must keep `touch-action: none`** — dropping it hands
   every touch drag to the browser and the editor goes dead on touchscreens.
6. **A new hold-to-operate widget must be listed in `HOLD_WIDGETS`** so touch
   long-press stays disabled over it; otherwise a stationary hold on it pops the
   context menu and cancels the interaction. Its own menu items are still
   reachable on touch through **arrange mode**, where nothing owns a press —
   that is the whole reason `ownsHeldPress` short-circuits there.
7. **Never decode images (or any asset) inside `draw()`** — go through the
   `imageBitmap` cache; it returns null while loading and repaints via the
   load callback.
8. **`block.layout` order is z-order.** Anything that rebuilds the layout must
   preserve it, or fronts/backs silently reshuffle.
9. **Patch-mode hit-testing must respect `alpha === 0`** (`tangibleItemAt`) —
   a hidden widget that still eats taps reads as a haunted block. The same
   applies to `FaceText.decor`: printed artwork is never the item under the
   pointer in patch mode, or a section box swallows the whole panel's clicks.
10. **A widget drawn in two places goes through `facepaint.ts`.** Never
    re-implement widget painting, drag feel, or CV/MIDI markers for a new
    surface; the Dock exists as proof the seam is enough.
11. **A Dock tab must not start its own rAF loop** — it takes `onFrame` from
    the app's single loop, and only the visible tab of a visible Dock is
    ticked.
12. **A Dock tab's rail position comes from `order`**, never from registration
    (i.e. import) order.
13. **A docked widget clone shares its parameter but not its appearance.**
    Writing clone geometry/`control` back into `block.controls` (or the
    reverse) defeats the entire feature.
14. **A canvas inside `#app` sizes its backing store at `dpr × UI zoom`**
    (`fitCanvasBacking`). `zoom` does not change `devicePixelRatio`, so
    `cssW * dpr` is short by the zoom factor and the bitmap gets upscaled —
    the whole surface goes soft at any scale ≠ 1 while the DOM around it stays
    crisp. This is the *sharpness* half of the UI-scale trap; the *hit-testing*
    half is invariant 1.
15. **Anything sampled for display is sampled at device resolution.** Waveforms,
    spectra, any per-pixel scan: buckets follow physical pixels, or the result
    is visibly quantized on exactly the displays people care about.
16. **Modals do not stack.** `buildModal` empties `#modal-layer`, so opening a
    `promptModal`/`confirmModal` *from inside* another dialog destroys the
    caller. In-dialog confirmation and renaming are inline (see the image
    library in [`09-persistence-and-assets.md`](09-persistence-and-assets.md)).
17. **`showContextMenu` has no submenus** — a `"▸"` item reopens the menu at the
    stored anchor. Capture the anchor once when the menu opens; re-reading the
    pointer would walk the sub-list across the screen.
18. **Nothing that only *dims* a widget may make it unreachable.** Proximity
    focus is a paint weight, never geometry: it is safe precisely because a
    block is fully drawn before the pointer can reach it. A variant that moved
    or resized blocks would break ports, wires and hit-testing at once.

## Canvas-less surfaces: the Advanced / Clip target picker

The Clip and Advanced tabs follow the workspace **selection**. On a desktop
that is invisible plumbing — you click a block and the deep editor follows.

On a phone, or in the detached Dock window, **there is no workspace canvas**,
and selection is only ever written by clicking one. So both tabs sat on
whatever the *desktop* had selected. With nothing selected there, the Advanced
tab showed its placeholder — which reads exactly as "the EQ is broken: no
nodes, no curve, no analyzer", and flickers into life for one frame whenever a
relayout happens to coincide with a selection.

Selection itself was never the problem: it lives on `Block.selected`, so it
travels with the scene. The missing piece was that nothing on a canvas-less
surface could **write** it. `src/ui/targetpicker.ts` is that writer.

- Shown only when `document.body.classList.contains('dock-window')` — on the
  desktop it would be a second, worse way to do something clicking already does.
- Walks the **whole** scene, not just the open graph: a phone has no breadcrumb
  either, so a picker limited to the current level cannot reach a block inside
  a subpatch.
- `selectTarget` navigates **before** selecting, because `clearSelection` and
  `selectedBlocks` both operate on the open graph — selecting inside a subpatch
  without opening it sets a flag nothing reads.

### `plotRect` must measure what `draw` measures

`adveq.ts` drew from `canvasWrap.clientWidth` (with a comment explaining that
`fitCanvasBacking` pins the canvas's own style, so `canvas.clientWidth` is a
value we wrote rather than a measurement) — while `plotRect()` read
`canvas.clientWidth` anyway. The two must agree or the plot is **drawn in one
space and hit-tested in another**: the curve lands where the band handles are
not, and dragging a node does nothing. Worse before first layout, where
`canvas.clientWidth` is 0 and the `|| 600` fallback drew a 600-wide plot into a
300-wide phone canvas.

Last verified 2026-08-02: on `dock.html` at 375×812 with nothing selected on
the desktop, the picker lists the scene's EQ blocks, selecting one opens the
editor, and the curve renders (559 coloured pixels).

### A remote's chosen target must survive a scene snapshot

The desktop pushes a **full scene** on every non-param change, and
`adoptScene` installs its selection along with it — normally *nothing*, because
nobody is clicking on the desktop while the phone is being used.

So the block a remote picked got deselected out from under it on the next
desktop edit. `advancedCandidates()` then found nothing, `advanced.ts` called
`setTarget(null)`, and `adveq`'s `draw()` did:

```js
g.clearRect(0, 0, W, H);
if (!block) return;        // cleared, then bailed → a blank canvas, every frame
```

The user-visible result is "it renders for a second and then goes blank",
which is indistinguishable from a broken renderer — and cost several rounds of
diagnosis chasing the drawing code instead of the selection.

Two fixes, and both matter:

- `targetpicker.reapplyChosenTarget()` remembers what this surface chose and
  puts it back after every `adoptScene` (`src/dockwindow.ts`). It does **not**
  `touch('selection')` — that would bounce a scene straight back at the desktop
  for a selection it just sent us.
- `draw()` now paints "No EQ selected" instead of leaving a cleared canvas.
  **A blank canvas is never an acceptable failure state**: it cannot be told
  apart from a crash, and it is the reason this took as long as it did.

`__lpdock.applyScene` exposes the snapshot path so this is testable without a
live desktop on the other end.

### Deep-editor hit radii follow the pointer

`adveq`'s `nearestBand` used a fixed 16 px grab radius. That is right for a
cursor and hopeless for a fingertip ~10 mm across that hides its own target: the
editor draws perfectly on a phone and never registers a grab. It now uses
`grabSlop(16, e)` from the shared input standard (docs/14-input.md), which is
2.6× for touch and pen and byte-identical for a mouse. Any deep editor doing
its own hit testing must do the same.

Last verified 2026-08-02: on `dock.html` at 375×812, picking an EQ renders the
curve (496 coloured px) and it survives three consecutive desktop snapshots
carrying no selection.

## The side dock zones are desktop-only (`styles.css`, 2026-08-02)

`#dock-left` and `#dock-right` are hidden below 700 px. On a 375 px phone the
two of them took **114 px — 30% of the screen width** — to show panels squeezed
to ~55 px, which is narrower than any of their contents can be read at.
`.dock-v .panel` sets `min-width: 0`, so nothing stops the squeeze: the zones
just quietly become two grey strips down the sides.

Worth knowing because of how it presented. Reported as "a grey border, the app
isn't fullscreen", which sounds native — and a lot of effort went into the
Android splash theme, `windowFullscreen`, display cutouts and safe-area insets
before anyone measured. What settled it in one step was asking *which edges*:
left and right, when every system bar in portrait is top or bottom. After that,
`getBoundingClientRect()` on `#center` (`x58 w251` inside a 375 px viewport)
named the culprit outright.

The lesson is the same one as the EQ painter below: when a symptom has both a
native and a web explanation, measure the boxes before theorising about the
platform. `#app`, `#topbar` and `#workspace` were all full width the whole time,
which alone ruled out everything native.

Last verified 2026-08-02: at 375 px the canvas is 365 px wide (was 251) and both
zones are `display: none`; at 1280 px they return at 53 px and 61 px.

## A linear canvas painter must isolate its optional parts (`adveq.ts`, 2026-08-02)

`draw()` in a deep editor clears at the top and then paints in one linear pass:
background, grid, analyzer overlay, curves, handles. Two failure modes there
produce *exactly* the same picture — grid drawn, everything after it missing —
and neither leaves any other trace:

1. **A throw partway.** Whatever ran before the throw stays on screen, the frame
   loop retries, and the same partial frame repeats forever. A frame counter
   incremented at the top of `draw()` keeps climbing, so it looks healthy.
2. **A non-finite coordinate.** Canvas silently drops the *whole* path if any
   point is `NaN`/`Infinity` — no throw, no partial line, just nothing, with a
   perfect grid around it.

From outside, both read as "the layout collapsed" or "the curve is off-screen",
which is where a lot of time went. So:

* Optional overlays fed by data this file does not own — above all
  `runtime.visualFor()` on a **remote** surface, where the `VisualFeed` is
  rebuilt from frames pushed over the link rather than read from a live engine
  — get their own `try/catch`. The silhouette is expendable; the curve is the
  editor.
* `draw()` wraps `paintFrame()` and paints the caught error *onto the canvas*.
  Rule: never leave a blank or half-blank canvas that cannot say why.
* Non-finite curve points are counted into `window.__lpdiag.eq` rather than
  being invisible.

The Dock's connection pill (`dockwindow.ts`, tap it) prints all of this —
`EQ plot`, `bands`, `nan a/b`, `EQ handles`, `EQ THREW`, `analyzer threw`. That
readout exists because a remote device is the one place none of this can be
inspected from a devtools console.

Last verified 2026-08-02: `npm run typecheck` and `npm run build` green with the
guarded painter; the diagnostics block renders in the pill's detail panel.
